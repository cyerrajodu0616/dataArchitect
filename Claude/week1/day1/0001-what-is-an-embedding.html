What an Embedding Actually Is

Week 1, Day 1 — deep dive · Lesson 0001

You already know how to make two rows in a warehouse table "close" to each other: pick features, compute a distance. An embedding does the same job on unstructured text — except the features aren't yours to define. A neural network learned them from patterns in language, and what falls out is a vector: a fixed-length list of numbers that positions a piece of text in a space where semantic closeness = spatial closeness.

Two footwear listings land near each other despite sharing almost no exact words; the unrelated product sits far off — this is the whole idea in one picture.

1. The mechanism: contrastive training

Embedding models like text-embedding-3-small and text-embedding-3-large start from a transformer language model backbone, then get trained with a specific objective: given pairs of text known to be related (a search query and the doc that answers it, two paraphrases, a product title and its description), pull those vectors together. Given unrelated pairs, push them apart. Do this over billions of examples and a geometry emerges where "meaning" has spatial structure.

Worked example
Three sentences, run through an embedding model conceptually: 
A: "The customer returned the shoes because they didn't fit."
B: "Customer requested a refund on footwear due to sizing issue."
C: "The warehouse received a new shipment of stainless steel cookware."
A and B share almost no exact words but describe the same event — they'd land close together. C shares more surface vocabulary with neither, and would land far from both, despite being a normal retail sentence too. The model isn't matching words. It's matching what's being said.

2. Dimensions: coordinates, not concepts

text-embedding-3-small returns 1536 numbers per input; -large returns 3072. Neither model lets you point at dimension 812 and say "that's the retail-return dimension." The dimensions are jointly learned and only meaningful in combination — like how no single column in a customer table tells you "loyalty," but spend + frequency + recency together might.

OpenAI's v3 models were trained with Matryoshka representation learning: you can truncate the vector (keep only the first N of the 1536/3072 numbers) via the dimensions parameter and retain most of the semantic quality, trading a bit of accuracy for storage and query speed. This is a real lever you'll pull in Week 2 when you're sizing pgvector indexes.

retail angle Say your product catalog embedding is 1536-dim at full size but you're indexing 40M SKUs across regional catalogs. Truncating to 256 dims via the dimensions param could cut your pgvector index size and query latency substantially, and for a coarse "browse similar products" feature the accuracy loss may not matter — you'd want the full 1536 dims for a precision-sensitive task like fraud/return-pattern matching, though.

3. More worked examples — building the intuition

Example: near-duplicates in a catalog
"Men's Running Shoes, Size 10, Black"
"Men's Black Running Shoes - Size 10"
Near-identical vectors. This is exactly the mechanism behind catalog dedup: two SKUs entered by different vendors with different phrasing collapse to nearly the same point.
Example: same words, different meaning
"I need a light jacket for spring."
"Turn off the light before you leave."
Both use "light," but context resolves it — "light" here means weight-of-garment vs. illumination. Because embeddings are computed over the whole sentence (not per-word, though token-level context feeds into it), the two vectors land far apart despite the shared token. This is precisely what keyword search gets wrong and embeddings get right.
Example: same meaning, opposite words
"This blender is excellent — highly recommend."
"Terrible blender, would not recommend."
These are not close together, even though both are "reviews about a blender." Sentiment is part of what the model captures — a naive bag-of-words overlap metric might see two review-shaped sentences and call them similar; a good embedding separates them by polarity. Worth remembering when you design retrieval for a customer-service RAG system in Week 8 — semantic similarity is not the same as "relevant to the same resolution."

4. Where this bites in practice

Two failure modes worth pre-loading before Week 3 (RAG):

  • Homonyms across domains. "Apple" the fruit and "Apple" the brand embed differently depending on surrounding context — but if your chunks are too short (a lone product title with no category context), the model has less to disambiguate with.
  • Numbers and exact identifiers embed poorly. SKUs, model numbers, exact prices — embeddings capture semantic meaning, not exact-match precision. "SKU-88213" and "SKU-88214" may sit almost as close together as "SKU-88213" and itself. This is the reason hybrid search (keyword + vector) matters for retail catalogs — you'll hit this directly in Week 2, Day 4.

5. Why this technique exists at all

Worth knowing the lineage — it's the difference between "embeddings = AI search" and actually understanding what problem they were built to solve.

Legacy techniques (inverted index, trigrams, edit distance) are all lexical — they measure character/string overlap. That's a hard ceiling: no amount of tuning lets an n-gram index match "AmEx" to "American Express Company", because there's no shared characters to index on. The signal isn't in the characters, it's in what the words refer to.

  • Word2Vec / GloVe (2013–14) — proved meaning could be represented geometrically and learned automatically from raw text (no hand-labeling). Famous proof point: king - man + woman ≈ queen. Limitation: one fixed vector per word, so "bank" (river) and "bank" (finance) got the same vector.
  • Transformers / BERT (2018+) — vectors became context-dependent, computed per full input. This is what solves the "light jacket" vs. "turn off the light" case above.
  • Sentence-level contrastive embeddings (Sentence-BERT 2019 → OpenAI's text-embedding-* line) — optimized so whole sentences/paragraphs, not just words, land in a comparable space. Direct ancestor of what you use today.
  • The mass-adoption catalyst: RAG (2022–23). Once people needed to retrieve relevant chunks to feed an LLM, embeddings became the standard retrieval mechanism — cheap via API, no labeled training data required, works out of the box across any domain. That's what pulled embeddings from NLP research into everyday data infrastructure, including your pgvector-backed personal agent.
interview framing Embeddings weren't invented to replace entity resolution — they were invented for semantic search/retrieval in language understanding. Entity-matching and dedup borrowed the technique afterward because "is this the same entity" and "is this text semantically related" share the same underlying math. Knowing *why* a tool exists, not just *that* it exists, is the depth that separates an architect from someone who only knows the API surface.

Appendix — Tokenization & Attention (optional, conceptual, no math)

Not part of the core 12-week path — extra depth for your own intuition, underneath everything above. Two ideas: how text gets chopped up before the model sees it, and how the model decides what to pay attention to once it has.

Tokenization: text isn't read a word at a time

Before anything else happens, your input string is broken into tokens — usually subword pieces, not whole words. A tokenizer trained via byte-pair encoding (BPE) or similar starts from individual characters and iteratively merges the most frequent adjacent pairs across a huge corpus, building up a fixed vocabulary of ~50k–100k common chunks.

Worked example
"unfitted"     → ["un", "fit", "ted"]
"parkway"      → ["park", "way"]
"SKU-88213"    → ["SK", "U", "-", "882", "13"]  (roughly — exact split varies by tokenizer)
Common whole words often stay as one token. Rare words, made-up words, typos, and identifiers get split into smaller, more common fragments. This is exactly why "SKU-88213" embeds poorly for exact matching from the main lesson — the tokenizer breaks it into generic numeric/ symbol fragments that carry very little distinguishing signal, the same fragments a thousand other SKUs would also produce.

Practical consequence: token count ≠ word count. This is why OpenAI bills and limits by tokens, not words or characters — and why chunk-size decisions in Week 3 (RAG) are made in tokens, not sentences.

Attention: how the model decides what matters, per word

Once text is tokenized, each token gets an initial vector (an embedding lookup — ironically, a smaller embedding table is the very first step inside the model). The transformer then runs several layers of self-attention: for every token, the model asks "which other tokens in this input should influence my meaning right now?" and reweights the token's vector based on the answer.

Worked example — this is how context resolves ambiguity
"I need a light jacket for spring."
When the model processes the token "light," self-attention lets it look at "jacket" nearby and "spring" further along, and weight those heavily — pulling "light" toward its weight-of-garment sense rather than its illumination sense. In 
"Turn off the light before you leave."
the same token "light" attends instead to "turn off" and "before you leave" — pulling it toward illumination. Same starting token, different final vector, purely because attention lets context reshape it layer by layer. This is the mechanism behind the "light jacket" example earlier in the lesson — now you've seen why it happens, not just that it happens.

Stack many attention layers, and by the final layer every token's vector encodes a rich, fully contextualized representation of "this word, in this exact sentence." Pooling (mentioned earlier) then compresses all those per-token vectors into the single sentence/paragraph vector you actually get back from the embeddings API.

retail angle This is also why a product description with more surrounding context ("Men's lightweight running jacket, breathable mesh, spring/fall wear") embeds more precisely than a bare title ("Light Jacket") — attention has more real context to work with, and the resulting vector encodes more disambiguated meaning. A recurring lever in retail catalog embedding quality: richer input text generally beats terser input text, up to the point of diminishing returns / cost.
