1. What "Fine-Tuning" an Embedding Model Actually Does to Weights

Fine-tuning is not LLM instruction fine-tuning. There is no chat template, no RLHF, no system prompt. Instead, you are adjusting the attention weight matrices (Q, K, V projections in every transformer layer) using a contrastive signal: pairs of texts that should be close, and pairs that should be far. The loss function measures the violation of that geometric requirement and back-propagates gradients into the weights to fix it.

Deep Dive: What exactly changes in the transformer weights?

A standard BERT-style transformer has 12 layers. Each layer contains 3 projection matrices:

  • WQ — maps a token's hidden state → query vector for attention
  • WK — maps a token's hidden state → key vector for attention
  • WV — maps a token's hidden state → value vector for attention

During fine-tuning on contrastive pairs, the gradient ∇L propagates back through the pooling operation (mean of all token hidden states → sentence vector) and then through all these weight matrices. The result: domain-specific terms ("steel toe", "SKU-9921") get more distinctive activation patterns relative to superficially similar but irrelevant tokens ("steel blue denim").

Key point for architects: You are not adding new knowledge. You are reshaping the geometry of the existing embedding space so that your domain's proximity relationships are better preserved. The model still can't understand tokens it never saw during pre-training unless you also expand the tokenizer vocabulary.

2. Loss Functions: Triplet Loss vs MNRLoss vs Contrastive Loss

Three loss functions dominate embedding fine-tuning. They differ in how many negatives they use per gradient step and how efficiently they pack information.

2a. Classic Triplet Loss

Given a triplet (Anchor, Positive, Negative), the loss enforces a margin m:

ℒtriplet = max(0, d(A, P) − d(A, N) + m)
  • d(A, P) = distance from anchor to positive (want small)
  • d(A, N) = distance from anchor to negative (want large)
  • m = margin hyper-parameter (typically 0.2–0.5)
  • Weakness: One negative per step. Requires careful curation of "hard" negative examples or training stalls early (gradient ≈ 0 when easy negatives are already separated far enough).

2b. MultipleNegativesRankingLoss (MNRLoss) — the industry standard

Also called in-batch negatives. Every other positive in the training batch becomes a negative for the current query. With batch size B = 64, you get 63 free negatives per query:

ℒMNR = −log ∑ exp(sim(q, pi)) / ∑j exp(sim(q, pj))

This is essentially cross-entropy over a soft-max of similarities within the batch. Why is it better than triplet loss?

  • Sample efficiency: Batch of 64 → 64 × 63 = 4,032 implicit (query, negative) pairs per step vs. 64 explicit triplets.
  • No margin hyper-parameter to tune.
  • Naturally calibrated — the model learns a relative ranking, not just a binary separated/not-separated decision.

2c. Contrastive Loss (Siamese)

ℒcontrastive = y · d² + (1 − y) · max(0, m − d)²

Where y = 1 for positive pairs and y = 0 for negatives. Used in older Siamese networks. Rarely preferred for text now because MNRLoss dominates on BEIR benchmarks.

3. Hard Negative Mining — The Difference Between Good and Great Fine-Tuning

Easy negatives: "steel toe boots" vs. "stainless steel saucepan" — any model will rank these apart. Gradient signal is near zero. Training stalls.

Hard negatives: "steel toe boots" vs. "steel blue work jeans" — lexically very similar, semantically different. Maximum gradient signal. This is where the model actually learns.

Hard Negative Mining Strategy

1. Run BM25
Get top-100 keyword matches for each query
→
2. Embed + Score
Bi-encoder cosine scores for top-100
→
3. Filter
High BM25, low cosine = hard negative
→
4. Train
MNRLoss on (query, positive, hard_neg)

This approach (called ANCE — Approximate Nearest Neighbor Negative Contrastive Estimation) typically yields a 3–8% nDCG@10 improvement over random negatives on domain datasets.

Why does easy negative training produce degenerate embeddings?

Consider the loss gradient for a very easy negative — an example where the model already separates the anchor and negative by a large margin. The gradient contribution from that pair is approximately 0 because the softmax denominator is dominated by the positive term. The optimizer sees nothing useful and makes trivially small parameter updates.

Over thousands of steps, the embedding space collapses toward a configuration that satisfies the easy negatives but fails to learn fine-grained semantic distinctions. This is called dimensional collapse — a pathology where the effective dimensionality of the embedding space shrinks to far fewer useful dimensions than the model has capacity for.

Mitigation strategies:

  • Large batch sizes (≥128) to increase in-batch hard negative density.
  • ANN-based hard negative retrieval (ANCE).
  • Temperature scaling on the softmax (τ ≈ 0.05–0.1) to sharpen the contrastive signal.

4. Hybrid Search (BM25 + Dense Vector) — The Engineer B Solution

Before touching model weights, the standard production move is Hybrid Search: combining an inverted-index keyword scorer (BM25) with a dense vector similarity scorer. This handles the common failure mode of domain-specific exact strings (SKUs, part numbers, brand names) that off-the-shelf embedding models struggle with.

4a. How BM25 Works (The Physics)

BM25 (Best Match 25) is a probabilistic retrieval function. For query term t in document d:

BM25(t, d) = IDF(t) × TF(t,d) × (k₁ + 1) / TF(t,d) + k₁ × (1 − b + b × |d| / avgdl)
  • IDF(t) = Inverse Document Frequency — rare terms score higher (e.g., "SKU-9921" appears in 1 doc → high IDF). This is the key reason BM25 is great for part numbers.
  • TF(t,d) = Term Frequency in document d
  • k₁ ≈ 1.2–2.0: saturation constant (prevents super-frequent terms from dominating)
  • b ≈ 0.75: length normalization (long documents don't automatically win)
  • avgdl = average document length across corpus

Why BM25 alone fails for semantic search: "comfortable shoe" and "footwear that reduces fatigue" have zero token overlap. BM25 score = 0. Dense vector search scores them high because it maps to the same semantic neighborhood.

4b. Reciprocal Rank Fusion (RRF) — Combining BM25 + Dense Scores

You cannot simply add BM25 and cosine scores — they have incompatible scales (BM25 is unbounded; cosine is [−1, 1]). The standard production solution is Reciprocal Rank Fusion:

RRF_score(d) = 1/(k + rank_BM25(d)) + 1/(k + rank_dense(d))

k = 60 (empirically stable default). You add the reciprocal of each system's rank. A document that is #1 in both lists gets 1/61 + 1/61 ≈ 0.033 — the highest possible score. Rank-based fusion is scale-invariant — no normalization needed.

5. BEIR Benchmark — How to Objectively Measure "Should I Fine-Tune?"

The BEIR benchmark (Benchmarking IR) is the industry-standard suite of 18 heterogeneous retrieval datasets. The primary metric is nDCG@10 (Normalized Discounted Cumulative Gain at rank 10):

nDCG@10 = DCG@10 / IDCG@10    where    DCG@10 = Σi=1..10 reli / log₂(i+1)

Relevance rel_i is graded (0, 1, 2). A perfect ranking gets nDCG@10 = 1.0. Random gets ~0.1.

6. The Fine-Tuning Data Pipeline — What You Actually Need

Fine-tuning is only as good as its training data. The minimum viable dataset for domain embedding fine-tuning:

  • ≥10,000 (query, positive_document) pairs — below this, validation curves are noisy and results are unreliable.
  • Source of truth for positives: click-through logs (user clicked → purchased = strong positive), expert annotations, or query-to-FAQ mappings.
  • Hard negatives: generated via BM25 retrieval (high BM25 rank but explicitly not-purchased/not-relevant).

7. MLOps Cost of Maintaining Fine-Tuned Embeddings

Fine-tuning is not a one-time event. It creates an ongoing maintenance obligation that most teams underestimate.

Full MLOps burden list — click to expand
  • Catalog drift: New SKUs/categories added. If new product language isn't in fine-tune training data, model reverts to off-the-shelf performance for those items.
  • Query distribution shift: Seasonal trends ("holiday gifts for him") change search language. Need periodic retraining.
  • Re-embedding pipeline: Every time model weights change, you must re-embed your entire product catalog (10M SKUs × 100 tokens = 1B tokens × embedding cost).
  • A/B testing infrastructure: Online evaluation of new model version vs. old. Shadow indexing required to avoid customer-facing degradation.
  • Model version registry: Git for model weights, reproducibility, rollback capability.
  • Embedding index rebuild: pgvector / Pinecone / Weaviate index must be rebuilt from scratch when vector space changes (non-backward-compatible).
  • Latency monitoring: Fine-tuned models may be larger and slower than the off-the-shelf base model they replaced.

Rule of thumb: Budget 0.5–1 FTE (ML Engineer) to maintain a production fine-tuned embedding model. If you don't have this capacity, use hybrid search + reranking instead.

"""
Week 1, Day 4 — Code 1: Fine-Tuning BGE with MultipleNegativesRankingLoss

Demonstrates end-to-end embedding fine-tuning on a synthetic retail dataset:
  - Building (query, positive_document) training pairs
  - Hard negative mining via BM25 rank + embedding score filter
  - Training with MNRLoss
  - Evaluating nDCG@10 before and after fine-tuning

Requires:
  uv add sentence-transformers rank-bm25 datasets
"""

from sentence_transformers import SentenceTransformer, InputExample, losses
from sentence_transformers.evaluation import InformationRetrievalEvaluator
from torch.utils.data import DataLoader
from rank_bm25 import BM25Okapi
import numpy as np

# ── 1. Toy Retail Training Dataset ──────────────────────────────────────
# In production: replace with click-through logs or human annotations.
TRAINING_PAIRS = [
    ("steel toe work boots",         "Men's Waterproof Steel Toe Safety Boots – SKU-9921-ST"),
    ("lightweight running sneakers",  "Women's Cushion Run Sneaker – Ultra-Light EVA Sole"),
    ("kids trail shoes size 7",       "Children's Trail Runner – Size 7K, Waterproof"),
    ("30 day return footwear",        "Footwear Return Policy: Full refund within 30 days of purchase"),
    ("leather casual loafers brown",  "Men's Genuine Leather Slip-On Loafers – Cognac Brown"),
    ("non-slip kitchen mat",          "Anti-Fatigue Kitchen Mat – Non-Slip Rubber Base 18x30in"),
    ("insulated water bottle 32oz",   "Stainless Insulated Tumbler – 32oz Keep Cold 24hrs"),
    ("waterproof hiking backpack",    "45L Adventure Backpack – IPX5 Waterproof, Osprey-style"),
]

# ── 2. Build InputExample list for MNRLoss ───────────────────────────────
# MNRLoss needs InputExample(texts=[query, positive]).
# In-batch negatives are the other positives in the same batch.
train_examples = [
    InputExample(texts=[q, p]) for q, p in TRAINING_PAIRS
]

# ── 3. Load base model ───────────────────────────────────────────────────
print("Loading base model bge-small-en-v1.5...")
model = SentenceTransformer("BAAI/bge-small-en-v1.5")

# ── 4. DataLoader + Loss ─────────────────────────────────────────────────
# batch_size controls how many in-batch negatives are available.
# In production use batch_size >= 64 for meaningful hard-negative density.
train_dataloader = DataLoader(train_examples, shuffle=True, batch_size=4)
train_loss = losses.MultipleNegativesRankingLoss(model)

# ── 5. Hard Negative Mining (BM25-assisted) ──────────────────────────────
# Find documents that score high on BM25 (lexical match) but are NOT the
# relevant positive. These are the most instructive negatives.
print("\nMining hard negatives via BM25...")
corpus = [p for _, p in TRAINING_PAIRS]
tokenized_corpus = [doc.lower().split() for doc in corpus]
bm25 = BM25Okapi(tokenized_corpus)

hard_negative_pairs = []
for query, positive in TRAINING_PAIRS:
    query_tokens = query.lower().split()
    bm25_scores = bm25.get_scores(query_tokens)

    # Get top-3 BM25 hits
    top_idxs = np.argsort(bm25_scores)[::-1][:3]
    for idx in top_idxs:
        candidate = corpus[idx]
        # Only add if NOT the ground-truth positive
        if candidate != positive:
            hard_negative_pairs.append((query, positive, candidate))
            break

print(f"Found {len(hard_negative_pairs)} hard negative triplets:")
for q, p, n in hard_negative_pairs[:3]:
    print(f"  Q: {q[:40]}")
    print(f"  P: {p[:40]}")
    print(f"  N: {n[:40]}")
    print()

# ── 6. Train (demo: 1 epoch — production: 3-10 epochs on full dataset) ───
print("Starting fine-tuning (1 epoch demo)...")
model.fit(
    train_objectives=[(train_dataloader, train_loss)],
    epochs=1,
    warmup_steps=2,
    output_path="./finetuned-bge-retail",
    show_progress_bar=True,
)

print("\nFine-tuning complete. Model saved to ./finetuned-bge-retail/")
print("Next: run nDCG@10 evaluation comparing base vs. fine-tuned on held-out test set.")

"""
Week 1, Day 4 — Code 2: Hybrid Search (BM25 + Dense Vector) with RRF Fusion

Demonstrates why hybrid search handles exact SKU lookup AND semantic queries
without touching model weights.

Requires:
  uv add sentence-transformers rank-bm25 numpy
"""

import numpy as np
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer

# ── 1. Retail Product Catalog ────────────────────────────────────────────
CATALOG = [
    "Men's Waterproof Steel Toe Safety Boots – SKU-9921-ST",        # 0
    "Women's Cushion Run Sneaker – Ultra-Light EVA Sole – SKU-4410", # 1
    "Workwear Steel Blue Denim Jeans – Reinforced Rivets",           # 2
    "Children's Trail Runner – Size 7K – Waterproof – SKU-7712",     # 3
    "Stainless Steel Non-Stick 10pc Cookware Set",                   # 4
    "Men's Leather Slip-On Loafers – Cognac Brown – SKU-3301",       # 5
    "Cushioned Anti-Fatigue Insole – Fits Steel Toe Boots",          # 6
    "Footwear Return Policy: 30-day full refund on all shoes",       # 7
]

QUERIES = [
    "SKU-9921-ST",                         # exact part number — BM25 should win
    "comfortable footwear reduces fatigue", # pure semantic — dense should win
    "steel toe boots for work",             # hybrid advantage
]

# ── 2. BM25 Index ────────────────────────────────────────────────────────
tokenized_catalog = [doc.lower().split() for doc in CATALOG]
bm25 = BM25Okapi(tokenized_catalog)

# ── 3. Dense Embedding Index ─────────────────────────────────────────────
print("Loading bi-encoder...")
model = SentenceTransformer("BAAI/bge-small-en-v1.5")
doc_vecs = model.encode(CATALOG, normalize_embeddings=True)  # unit-norm for cosine

def bm25_rank(query: str) -> list[int]:
    """Return catalog indices sorted by BM25 score (best first)."""
    scores = bm25.get_scores(query.lower().split())
    return list(np.argsort(scores)[::-1])

def dense_rank(query: str) -> list[int]:
    """Return catalog indices sorted by cosine similarity (best first)."""
    q_vec = model.encode(
        f"Represent this sentence for searching relevant passages: {query}",
        normalize_embeddings=True
    )
    sims = doc_vecs @ q_vec  # dot == cosine since both normalized
    return list(np.argsort(sims)[::-1])

def rrf_fuse(ranks_a: list[int], ranks_b: list[int], k: int = 60) -> list[int]:
    """
    Reciprocal Rank Fusion: RRF(d) = 1/(k + rank_a(d)) + 1/(k + rank_b(d))
    Returns catalog indices sorted by fused score (best first).
    """
    scores = {}
    for rank, idx in enumerate(ranks_a):
        scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank + 1)
    for rank, idx in enumerate(ranks_b):
        scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=lambda x: scores[x], reverse=True)

# ── 4. Run All Three Modes ───────────────────────────────────────────────
print("\n" + "="*65)
print("HYBRID SEARCH DEMO — BM25 vs Dense vs RRF Fusion")
print("="*65)

for query in QUERIES:
    bm25_results = bm25_rank(query)
    dense_results = dense_rank(query)
    rrf_results  = rrf_fuse(bm25_results, dense_results)

    print(f"\nQuery: \"{query}\"")
    print(f"  BM25  Top-1: {CATALOG[bm25_results[0]][:55]}")
    print(f"  Dense Top-1: {CATALOG[dense_results[0]][:55]}")
    print(f"  RRF   Top-1: {CATALOG[rrf_results[0]][:55]}")
