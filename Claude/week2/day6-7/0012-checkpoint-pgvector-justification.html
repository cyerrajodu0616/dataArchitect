Most candidates answer "why pgvector" with preferences — simplicity, familiarity, cost. This ADR answers it with a capacity model and named migration triggers. ARCHITECTURAL DECISION RECORD (ADR-002)

Title: Vector Store Selection — pgvector vs Purpose-Built Vector Databases
Author: Yc (AI Data Platform Architect)
Status: Approved / Production
Supersedes: none  |  Related: ADR-001 (Embedding Model Selection)

1. Context

Workloads sharing this decision:

  • Personal Agent — LangGraph + Postgres + OpenAI embeddings. ~10,000 document chunks, low QPS, single tenant, interactive chat latency budget.
  • Retail platform (primary reference architecture) — 4M SKU embeddings at 1536 dims, 500 QPS peak, sub-100ms P99 target, catalog mutating every few minutes, 400 white-label storefronts.
  • Insurtech underwriting corpus — ~200k chunks of filed forms, riders and underwriting guidelines across carriers and states. Low QPS, PHI-derived embeddings, bitemporal form versioning, retrieval auditability.
  • Fintech — two distinct corpora that must not be conflated: ~150k document chunks (disclosures, dispute procedures) and ~2B transaction/merchant embeddings for fraud similarity at 4,000 QPS.

§7 states where the decision differs across these. The retail figures carry the analysis unless noted.

The question is not "which vector database benchmarks fastest." At this scale all candidates run HNSW variants and land within milliseconds of each other. The decisive question is where vector state lives relative to the source of truth, because that single choice determines whether freshness is a transaction or a pipeline.

3. Decision

Adopt pgvector (Option A) for both workloads. Revisit only when one of the four named triggers in §6 fires, with the specific numeric threshold met and evidenced.

4. Rationale — in priority order

  1. The dual-write problem is the dominant cost, and it is invisible on pricing pages. Any store that is not Postgres makes the SKU write and the vector write two writes to two systems. That obliges a transactional outbox, a CDC consumer with idempotent upserts, a retry policy and dead-letter queue, a nightly reconciliation sweep, drift alerting, and a runbook for "the two systems disagree." Simulation of a 24-hour period at realistic catalog churn produced ~221,000 SKU-minutes of drift and ~17,000 customer searches/day touching a stale result. On pgvector all of those are zero by construction — the row and its embedding commit together.
  2. Managed does not mean operated. A vendor manages their index. The freshness contract with the catalog remains ours in every architecture. The managed boundary sits at their API, not at our correctness requirement.
  3. Hybrid search is achievable in Postgres, and is actually better there. The lexical index is a generated tsvector column maintained by the same commit as the product row — no sync, no drift. Weaviate's built-in hybrid is excellent but still sits on the far side of the dual-write boundary.
  4. Recall monitoring is easier on Postgres. Exact search is the ground truth for an approximate index, and Postgres lets us compute it with SET LOCAL enable_indexscan = off. A managed service that offers no exact-search mode cannot produce ground truth without exporting every vector.
  5. Non-technical factors decide the rest. Compliance sign-off already covers the existing Postgres deployment; a new store holding the same customer-derived data restarts security review and data-residency assessment. And the 3am on-call engineer can already read a Postgres query plan.
  6. For the Personal Agent specifically — at ~10,000 chunks the index is well under 100 MB. Any vector database is correct on capability grounds; the minimal-toolset principle makes adding one indefensible.

5. Capacity Model — the numbers behind the decision

pgvector's HNSW index stores a full copy of every vector (traversal needs it at each node to compute distance), so the index is ~105–115% of the heap at 1536 dims — not the 30–60% a pointer-based index would cost.

hnsw_per_row = dims×4 + (2×m)×8 B + ~24 B all over a ~0.9 fill factor = 6,144 + 256 + 24 /0.9 = ~7,138 B per row 4M SKUs -> heap 24.7 GB + HNSW index 28.6 GB = ~53 GB on disk RAM to keep the index cached: ~51 GB

Critically, pgvector does not degrade gracefully. HNSW traversal is serially-dependent pointer chasing at queue depth 1, so a fast SSD does not rescue an index that no longer fits RAM — you pay full per-read latency once per hop. The result is a cliff, not a slope: ~2ms cached → ~10ms on local NVMe → 50–100ms on network SSD.

6. Migration Triggers — the answer to "when would this break?"

Trigger 1 — Volume
HNSW index + 1.8× headroom exceeds affordable single-node RAM (~50M vectors at 1536 dims after mitigation)
Replication does not help: every replica holds a complete copy, so replication scales QPS but never corpus size. → Milvus / Zilliz, or pgvectorscale StreamingDiskANN first.
Trigger 2 — Tenancy
Hundreds of tenants with skewed traffic requiring per-tenant index isolation and hot/cold tiering
A shared HNSW graph with a tenant_id filter makes recall a function of tenant size — small storefronts silently get worse search, and no default dashboard segments recall by tenant. Postgres offers table-per-tenant or RLS, but no offload-to-object-storage for dormant tenants. → Weaviate (tenant shards) or Pinecone (namespaces).
Trigger 3 — Write velocity
Sustained embedding ingest saturates the instance serving queries; REINDEX cannot fit a maintenance window
In Postgres, index build and live queries share one machine. → Milvus (dedicated index nodes).
Trigger 4 — Team shape
No Postgres operations capability on the team at all
→ Pinecone (fewest knobs). Note this inverts our situation rather than describing it.
Escape hatches to exhaust before any migration

7. Domain Applicability

This ADR is written against the retail reference architecture. The same model applied to two adjacent domains gives materially different answers, which is stated here so the decision is not over-generalised.

Retail — as specified

4M × 1536 · 500 QPS

Index 28.6 GB, needs ~51 GB. Fits a 64 GB instance.

Decision: pgvector. First constraint is CPU contention with OLTP → dedicated read replica.

Life insurance / insurtech

~200k × 1536 · 20 QPS

Index 1.4 GB. No wall reachable — 35× growth before RAM is a conversation.

Decision: pgvector, and it isn't close. PHI keeps the vector inside the existing compliance perimeter; bitemporal form versioning and retrieval auditability are the real engineering.

Fintech — split by corpus

docs 150k · txns 2B × 768

Documents look exactly like insurance. Transaction embeddings need 13.4 TB resident — 26× a 512 GB box, and the full mitigation ladder still leaves ~1.5 TB.

Decision: pgvector for documents, sharded store for transactions. One company, two answers.

The generalisation to avoid
"pgvector is the right default" is not what this ADR concludes. It concludes that at the stated corpus size, QPS, and tenancy, co-location's transactional freshness outweighs what a purpose-built store adds. Change the corpus by three orders of magnitude — the fintech transaction case — and the same model recommends sharding. An architect who cannot name the conditions under which their own decision reverses has stated a preference, not a decision.

8. Cost-Optimised Variant (for a budget-constrained employer)

The decision above optimises for correctness and operational simplicity. Where cost dominates — an early-stage startup, or a team explicitly asked to cut infrastructure spend — the same analysis produces a second, defensible answer. Both are stated so the tradeoff is explicit rather than implied.

The cost-optimised architecture, when the crossover is passed
Keep the vector column in Postgres. Drop only the index. An unindexed vector column costs disk rather than RAM, and Postgres continues to provide the durable source of truth for index rebuilds, transactional writes, and the full-precision corpus the rerank stage needs. Search moves to an external FAISS IVF-PQ index (64 bytes/vector, ~87× smaller) returning IDs, which Postgres hydrates and filters.

This is strictly better than the commonly-drawn "Postgres holds metadata only" version, which discards all three of those properties and still has to store the vectors somewhere durable.

What the saving costs — state this unprompted
Recall falls from 0.98 to ~0.94 and only holds there because of the rerank stage. You accept a freshness lag set by rebuild cadence, lose SQL WHERE inside the index, lose MVCC, and put a service on the on-call rotation. The compression applies to what must be in RAM — not to what must exist.
Q: "How would you cut our vector search bill?"

"First I'd check where we are against the crossover, because below roughly 10M vectors the answer is to do less, not more — an external quantized service costs more than pgvector once you price the 0.2 FTE to run it. Above it the lever isn't the ANN library, it's the encoding: at 1536 dims the vector is 6,144 bytes and the graph is 136, so compressing the vector is the only thing that moves the bill. int8 scalar quantization is 4× for about a point of recall and is the most underused option available. Product quantization gets to 64 bytes — 87× — but raw recall drops to ~0.75, so it only works with a rerank stage against full-precision vectors, which means keeping those vectors in the Postgres heap. At 100M that's about $29k/month down to $3.9k, and I'd want a golden-set recall job running before I shipped any of it, because every one of those levers trades quality for cost and the failure is silent."

Q: "You used AI coding tools — doesn't that make this less impressive?"

"It makes the build faster, not the system cheaper to own. I modelled it: dropping the build from four weeks to one moves the all-in cost at 100M vectors from $3,577 to $3,144 a month — about 12% — because the ongoing operational load dominates and doesn't shrink. What agents genuinely change is reach: a small team can now ship an architecture that used to need a bigger one. The judgment about whether to build it, and where the crossover sits, is still the part that matters."

9. Consequences

Accepted:

  • Single-node volume ceiling; migration required past ~100M vectors.
  • Blast radius — search and OLTP share a failure domain. Mitigated by routing search to a dedicated read replica.
  • Vector data inflates backup size and PITR restore time for the whole database.
  • ts_rank_cd has no IDF term, so lexical ranking is weaker than true BM25. Acceptable because RRF uses rank, not score; ParadeDB is the upgrade path if it bites.
  • Graph decay from catalog churn requires scheduled REINDEX CONCURRENTLY with 2× index disk headroom.

Required follow-on work:

  • Nightly golden-set recall@10 monitoring on a read replica, alerting on the mean and paging per query class. Non-negotiable: measured decay of 0.99 → 0.87 over six months of churn with every SRE dashboard green.
  • Alerting on the HNSW index's own cache-hit ratio (pg_statio_user_indexes) as the RAM-cliff leading indicator — the database-wide ratio will not show it.
  • Query-class routing for hybrid search, with exact identifiers short-circuiting to a btree lookup rather than being fused.
  • Quarterly re-run of the capacity model against actual catalog growth.

Interview Drill

Q: "Why did you use pgvector instead of a real vector database?"

"Because the hard part at our scale isn't the ANN index — it's the freshness contract with the catalog. pgvector makes that a transaction: the SKU row and its embedding commit together, so a stale or orphaned vector is structurally impossible. Every other option makes it a pipeline — outbox, CDC, reconciliation, drift alerting — that I have to build, staff, and page someone for, and that appears on no vendor's pricing page. I modelled it: a day of realistic catalog churn produces around 17,000 customer searches touching a stale result. So I'd need a scale, tenancy, or write-velocity requirement Postgres genuinely can't meet before taking on a second system — and I named those thresholds up front rather than waiting to be surprised."

Q: "At what point does that stop being true?"

"When the HNSW index no longer fits one machine's RAM, because traversal is serially-dependent pointer chasing — a fast SSD doesn't save you, since you're at queue depth 1 and pay full read latency per hop. It's a cliff: 2ms to 80ms, not a slope. At 1536 dims that's about 7 GB of index per million vectors. Under 10M is trivial; 25–50M is viable once I apply fp16 and MRL truncation, which measure at 4.9× combined rather than the 6× you'd get by multiplying naively, because the graph overhead is fixed. Past ~100M the in-Postgres ladder is exhausted and sharding is the only structural answer — replication can't help, since every replica needs the whole index. In practice, though, I'd expect to hit the CPU wall before the RAM wall if search shares the OLTP instance, so the first move is a dedicated read replica, not a new database."

Q: "What would you monitor?"

"Recall@10 from a golden query set, nightly, on a read replica — because it's the one signal missing from every default dashboard. Latency, error rate and cache-hit ratio all stay green while approximation quality decays from graph churn, stale centroids, or someone lowering ef_search to silence a latency alert. I simulated six months of churn: recall fell from 0.99 to 0.87 while work per query moved 6%, which trips no alert anyone has ever configured. Exact search is the ground truth, so it's a job, not a research project. And I'd alert on the mean but page per query class, because a small high-intent segment can collapse while the average looks fine."
