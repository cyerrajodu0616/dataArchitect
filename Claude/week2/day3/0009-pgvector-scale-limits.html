Scale Tradeoffs — Where pgvector Actually Breaks

Week 2, Day 3 — the five walls, in the order you hit them, with numbers

Day 2 named four migration triggers. The volume one was the vaguest — "roughly 50M+ vectors." That is not an architect's answer; it is a number repeated from blog posts. Today we derive it, because in an interview the follow-up is always "why that number?" and the credible answer is a capacity model, not a threshold you memorised.

The thing to internalise today
pgvector does not degrade gracefully. Four of its five limits are cliffs, not slopes — the system is fine, then a threshold is crossed and P99 latency moves by 25–100×. Knowing where each cliff sits, and which one you hit first, is the whole skill.

1. The Real Memory Model (Refining Day 1)

Day 1 used a rule of thumb: "HNSW adds ~30–60% on top of the heap." That is fine for a back-of-envelope, and wrong for capacity planning. The reason matters:

pgvector's HNSW index stores a full copy of every vector inside the index.

The index is not a set of pointers into the heap — traversal needs the vector at each node to compute distance, so the vector is duplicated. The correct per-row model:

vector_bytes = dims × 4 # float32; halfvec = dims × 2 heap_per_row = vector_bytes + ~40 B # tuple header + your other columns hnsw_per_row = vector_bytes # the duplicated copy + (2 × m) × 8 B # neighbour list: layer 0 holds 2m links + ~24 B # element header index_total = N × hnsw_per_row / 0.9 # ~90% page fill factor

For the running example — 4M SKUs, 1536 dims, m=16:

ComponentPer row× 4M rows
Vector payload6,144 B24.6 GB
Heap (vector + tuple overhead)~6,184 B24.7 GB
HNSW neighbour lists (2×16 links × 8 B)256 B1.0 GB
HNSW index total (incl. vector copy, fill factor)~7,138 B28.6 GB
Combined on disk—~53 GB

So the index is roughly 105–115% of the heap, not 30–60%. At 1536 dims the vector copy dominates everything else; the graph itself is under 4% of the index. That single fact drives every mitigation later in this lesson — shrink the vector and everything shrinks.

When does the graph overhead actually matter?

Only at low dimensionality. The neighbour list is a fixed 2m×8 bytes regardless of dims:

  • 1536 dims: vector 6144 B vs links 256 B → links are 4% of the index.
  • 384 dims (bge-small): vector 1536 B vs links 256 B → links are 14%.
  • 64 dims: vector 256 B vs links 256 B → links are half the index.

Practical consequence: raising m from 16 to 48 for better recall costs you ~4% more index at 1536 dims but ~40% more at 384 dims. The "just increase m" advice has very different price tags depending on your embedding size.

2. Wall #1 — RAM, and Why It Is a Cliff

1

The index must live in memory. When it doesn't, you fall off an edge.

Postgres has no vector-specific cache. Index pages compete for shared_buffers and the OS page cache like any other relation. While the working set fits, HNSW traversal is pure memory access at ~2ms. When it doesn't, every graph hop becomes a disk read.

Here is the part most people get wrong, and it is the best thing you can say on this topic in an interview:

HNSW traversal is pointer chasing. Each hop's address depends on the previous hop's result.

You cannot prefetch it, you cannot parallelise it, and queue depth does not help. A NVMe drive rated for 500k IOPS delivers that number at queue depth 64 — but graph traversal runs at queue depth 1. What you actually pay is raw per-read latency, once per hop, serially.

StorageRandom read latency (QD1)~100 dependent hopsRegime
RAM (page cache hit)~100 ns~2 ms total queryDesign target
Local NVMe~80–100 µs~10 msDegraded but survivable
EBS gp3 / network SSD~500 µs – 1 ms50–100 msP99 collapse

Note the shape: nothing warns you. Capacity dashboards show healthy latency right up to the knee, because until the working set exceeds cache the miss rate is ~0. Then it goes non-linear over a matter of weeks of catalog growth.

The monitoring you need before you need it
Track shared_buffers hit ratio for the vector index specifically via pg_statio_user_indexes (idx_blks_hit vs idx_blks_read). A hit ratio drifting below ~99% on the HNSW index is the leading indicator of the cliff. Aggregate database cache-hit ratio will look fine and tell you nothing — the vector index is a small fraction of total block accesses right up until it isn't.

3. Wall #2 — CPU and the QPS Ceiling You Share With OLTP

2

Vector search is CPU-bound, and it is competing with your application's normal queries.

Per query, HNSW at ef_search=100 performs on the order of several hundred distance computations. Each 1536-dim cosine distance is ~6 KB of memory traffic and ~1,536 fused multiply-adds — SIMD makes the arithmetic nearly free, so it is memory-bandwidth bound, not FLOP bound.

Planning heuristic (validate with pgbench on your own hardware before quoting it):

~200–400 QPS per core at 1536 dims, ef_search=100, index fully cached

The architectural point is not the number — it is whose cores those are:

  • A 16-vCPU instance gives you a theoretical ~3,000–6,000 vector QPS.
  • But that same instance is serving your order writes, inventory reads, and session queries.
  • At 500 vector QPS you have consumed 1.5–2.5 cores continuously. At Black Friday's 2,000 QPS you have consumed 6–10 cores, and your checkout transactions are now queueing behind product searches.

This is the failure mode nobody plans for: the vector workload does not fall over — your OLTP workload does. A latency regression in checkout traced back to search traffic is a genuinely bad incident, and it is an argument for isolation (a read replica dedicated to search) long before it is an argument for a different database.

4. Wall #3 — Writes, Bloat, and the Cost of Rebuilding

3

HNSW inserts are graph mutations, and deletes leave tombstones the graph can't forget.

An HNSW insert is not an append. It runs a search to find neighbours, then updates bidirectional links on existing nodes — meaning a single insert dirties pages scattered across the index, which then flow through WAL and out to your replicas.

OperationCost characteristicWhat it does to you at 4M rows
Single INSERT~1 search + link updates on ~2m nodesRoughly an order of magnitude more expensive than a b-tree insert
UPDATE of embeddingDelete + insert (new heap tuple)Old graph node becomes a tombstone
DELETEMarks dead; graph node remains as a traversal waypointRecall and latency drift as dead ratio grows
VACUUMReclaims heap; HNSW cleanup is limitedDoes not restore an over-churned graph's quality
REINDEX CONCURRENTLYFull rebuild; needs ~2× index spaceTens of minutes to hours, +29 GB transient disk
The seasonal-catalog trap
Retail catalogs churn hard twice a year. A collection that is 30% re-embedded and 10% delisted over a season leaves a graph whose links point through large numbers of dead nodes — you pay traversal cost for entries that can never be returned. Recall degrades silently; latency creeps. The fix is a periodic REINDEX CONCURRENTLY, which means you need a maintenance window with 2× index headroom on disk, and it competes for the same CPU serving queries (Day 2's Milvus contrast: dedicated index nodes exist precisely to avoid this).
-- Bulk load pattern: never insert into an existing HNSW index at volume. -- Build the index AFTER the load; it is dramatically faster and yields a better graph. DROP INDEX IF EXISTS products_embedding_hnsw; -- Give the build room, or it spills to disk and takes hours instead of minutes. SET maintenance_work_mem = '16GB'; SET max_parallel_maintenance_workers = 7; -- pgvector parallelises HNSW builds CREATE INDEX CONCURRENTLY products_embedding_hnsw ON products USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

5. Wall #4 — Replica Economics

4

pgvector scales reads by replicating the entire index. That is linear cost, not sharding.

This is the most under-appreciated limit, and the cleanest way to explain why pgvector's ceiling is economic rather than technical.

To double read throughput you add a replica. But a replica is a full copy — it needs the whole 28.6 GB index resident in its own RAM to stay off the cliff. Contrast with Milvus, where adding a query node adds capacity against a sharded index; each node holds a slice.

The sentence that shows you understand the difference
"Replication scales QPS but not corpus size — every replica still needs the entire index in RAM. Sharding scales both. That is the structural reason pgvector has a volume ceiling and Milvus doesn't, and it's why the fix for 'we outgrew pgvector' is never 'add a replica'."

6. Wall #5 — Connections and Concurrency

5

Postgres is process-per-connection, and a slow query holds its process.

Little's Law: concurrent_connections = QPS × latency.

  • Healthy: 500 QPS × 2 ms = 1 concurrent connection. Trivial.
  • Post-cliff: 500 QPS × 80 ms = 40 concurrent connections — and each Postgres backend is a real OS process with its own work_mem.

The cliff therefore compounds: falling off it multiplies your connection count 40×, which exhausts the pool, which queues application threads, which turns a latency problem into an availability incident. Put PgBouncer in transaction mode in front of this before you need it.

Levers 1–3 are the ones to reach for first, and together they move the RAM cliff out by ~4.9×. That is the difference between "we outgrow this in 8 months" and "we outgrow this in four years" — usually longer than the architecture's planning horizon.

Why 4.9× and not 6×
The tempting arithmetic is 2× (fp16) × 3× (1536→512 dims) = 6×. That overstates it, because only the vector shrinks — the neighbour list (2m × 8 B = 256 B) and element header are fixed costs that survive every quantization. Per row: baseline 6,424 B → halfvec+MRL 1,304 B, a real 4.9×. The same effect makes lever 4's headline "32× on the vector" land at ~13.6× on the index. Run mitigation_ladder.py rather than multiplying in your head; this is exactly the kind of number an interviewer will ask you to derive.
Why binary quantization needs a second stage, and how to write it

Binary quantization reduces each dimension to one bit (sign). 1536 dims → 192 bytes instead of 6,144 — a 32× reduction. Distance becomes Hamming distance, which is a popcount instruction: extremely fast.

But one bit per dimension destroys enough information that top-10 results are no longer trustworthy on their own. The pattern is over-fetch then rescore: retrieve top-200 by binary distance from the small index, then compute exact cosine on those 200 full-precision vectors from the heap and re-sort.

-- Stage 1: cheap ANN over the binary index. Stage 2: exact rescore of 200 rows. WITH candidates AS ( SELECT id, embedding FROM products ORDER BY binary_quantize(embedding)::bit(1536) <~> binary_quantize($1) LIMIT 200 ) SELECT id, embedding <=> $1 AS distance FROM candidates ORDER BY distance LIMIT 10;

You keep the full-precision vectors in the heap (cheap, sequential access for 200 rows) and only the binary index needs to be RAM-resident. This is the single highest-leverage trick for staying on Postgres at scale.

8. Building the Index Outside Postgres

Wall #3 said an HNSW rebuild takes ~42 minutes at 4M vectors, needs 2× index space on disk, and competes with live queries for CPU. The natural question follows: can you build the index somewhere else — in C++, offline — and just hand the result to Postgres?

The answer has two halves, and they point in opposite directions.

Half one: you cannot import a prebuilt index into pgvector

Why not
A pgvector HNSW index is a Postgres index access method, not a file. It lives in the relation's own page format, is WAL-logged, participates in MVCC visibility checks, and is tied to the table's physical tuple identifiers. Postgres exposes no "load a prebuilt index" API for any index type — builds must go through the access method's build function.

So there is no supported path where you run hnswlib in C++, serialise the graph, and copy the bytes into a Postgres index. What you can do inside Postgres is make the build faster (maintenance_work_mem, max_parallel_maintenance_workers) and control when it runs — but the CPU is spent on the database host either way.

The in-Postgres workaround: build into a shadow table, then swap

You cannot move the build off the machine, but you can take it off the hot path and make cutover instant:

-- 1. Build the new generation beside the live one, at your chosen time. CREATE TABLE products_v2 (LIKE products INCLUDING ALL); INSERT INTO products_v2 SELECT * FROM products; -- or re-embedded rows SET maintenance_work_mem = '16GB'; SET max_parallel_maintenance_workers = 7; CREATE INDEX products_v2_emb ON products_v2 USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- 2. Cut over atomically — a metadata-only operation, milliseconds. BEGIN; ALTER TABLE products RENAME TO products_old; ALTER TABLE products_v2 RENAME TO products; COMMIT; -- 3. Keep products_old until you are confident. Rollback is another rename.

This gives you a versioned, rollback-able index generation without leaving Postgres. It costs 2× storage during the transition and still burns build CPU on the primary — run it on a schedule you control, ideally on an instance that is not also serving checkout.

Half two: you can move the index out entirely — and this is a real architecture

The pattern is to stop treating the index as part of the database and start treating it as a derived build artifact: Postgres remains the source of truth for vectors; the ANN index is a versioned file produced by a batch job and served by something else.

This will feel familiar. It is the same shape as a nightly aggregate table, a search index build, or an offline-to-online feature store materialisation — work you have done for years.

C/C++ librarySerialisable artifactWhy you'd pick it
FAISS (Meta)write_index / read_indexThe default. IVF, PQ, HNSW, and GPU index types. Build a billion-vector index on a GPU box in minutes.
hnswlibsaveIndex / loadIndexHeader-only C++ from the HNSW authors. Small, fast, easy to embed.
usearchmmap-able fileSingle-header C++, memory-mapped so load is instant and processes share one copy. Used inside ClickHouse.

Solving freshness: base + delta + tombstones

An immutable nightly artifact cannot see today's changes. The standard fix is a pattern you already know from LSM-trees and Lucene segments:

  • Base index — large, immutable, rebuilt on a schedule. Holds ~99% of vectors.
  • Delta index — small, in-memory, built from rows changed since the base was cut. Cheap to rebuild continuously.
  • Tombstone set — IDs deleted or updated since the base. Results matching it are dropped.
  • Query = search base + search delta → merge → filter tombstones → top-k.
Why this is your kind of problem
Base + delta + tombstone with periodic compaction is an LSM-tree. You have reasoned about write amplification, compaction cadence and read amplification before — this is the same tradeoff with vectors in the leaves. Most GenAI engineers arrive at this pattern by trial and error; you can name it, and name the failure mode (delta grows until querying it costs more than the base did, so compaction cadence is set by delta size, not by the clock).

What you gain, and what you have just signed up for

Gains

  • Build CPU leaves the database entirely — Wall #3 disappears
  • Build on a GPU box: hours become minutes
  • Index types pgvector lacks — PQ, ScaNN, GPU, DiskANN
  • Serving nodes are stateless — scale reads by pulling the artifact
  • Immutable, versioned, reproducible — you can re-run a query against the exact index that served it
  • mmap means the OS page cache handles residency, shared across processes

Costs

  • You have re-created the dual-write problem — Day 2's entire argument now applies to you
  • No SQL WHERE in the index — filtering moves to your code, and Day 1's pre-filter dilemma returns worse
  • No MVCC — the index has no concept of transaction visibility
  • Deletes need a tombstone set maintained separately
  • You now own a service: deploys, health checks, memory, on-call
  • Two round trips — index for IDs, Postgres to hydrate
The honest summary
Moving the index out is not a way to dodge Day 2's dual-write problem — it is a way to accept it in exchange for build isolation and index freedom. The difference from adopting Pinecone or Milvus is real but narrow: the artifact is derived and disposable, so a failure costs a rebuild rather than data loss, and Postgres stays the single authoritative copy. That is a genuinely weaker failure mode. It is not the same as "no sync pipeline."

The recommendation, and when it flips
For the retail case at 4M vectors, this is over-engineering: a 42-minute rebuild on a schedule you control, or a shadow-table swap, solves Wall #3 without a new service. insurance At 200k chunks it is emphatically not worth it — except that the immutability is attractive for audit, so a versioned artifact can be justified on reproducibility grounds even when performance doesn't need it. fintech At 2B transaction vectors it stops being optional: no in-Postgres lever reaches, the corpus is naturally batch-oriented, and PQ/GPU index types are the only affordable way to build at all.

9. The Cost Argument — Quantization Is the Real Lever

Everything so far has treated memory as a capacity problem. For a cost-sensitive employer it is a budget problem, and that reframing changes which lever you reach for. Start from the observation that has run through this whole lesson:

At 1536 dims the vector is 6,144 bytes and the HNSW graph is ~136.
The graph is 2% of your memory bill. Compressing the vector is the only lever that matters.

Section 7's ladder stopped at binary quantization because that is what pgvector offers. Outside Postgres the ladder goes considerably further.

The encodings, and what each costs in recall

How product quantization actually works — enough to explain it on a whiteboard

Split each 1536-dim vector into m contiguous subvectors. With m=64, each subvector is 24 dims. For each of the 64 positions, run k-means over the whole corpus to learn 256 centroids for that slice. Now any vector is encoded as 64 centroid IDs — and a centroid ID in 0–255 is exactly one byte.

1536 float32 = 6,144 bytes ↓ split into 64 subvectors of 24 dims ↓ replace each with the id of its nearest centroid (256 per slice = 1 byte) 64 bytes ~96x smaller

Distance is then approximated by summing precomputed distances to the centroids — a table lookup per slice rather than arithmetic over 1536 floats, so it is also faster, not just smaller.

What you lose: every vector is now approximated by the nearest point in a coarse codebook. Two genuinely different vectors can encode identically. That is why raw PQ recall sits around 0.75 and why the rerank stage is not optional.

OPQ (optimised PQ) applies a learned rotation before splitting, so the subvectors carry more balanced information. Same size, a few points better recall — take it if your library offers it.

The part that is usually left out of the pitch
"PQ gives you 96× compression" is true and incomplete. At 0.75 recall, PQ alone is unusable for most retrieval. You recover quality with rerank: retrieve top-200 using the compressed index, then rescore those 200 against full-precision vectors and re-sort.

Which means you still have to store the full vectors somewhere. The compression is on what must be in RAM, not on what must exist. Anyone who quotes the 96× without mentioning the rerank corpus has not built this.

Where to keep the full vectors — and the variant to argue for

You will see the architecture drawn as "Postgres holds metadata only, the ANN engine holds vectors." That works, but there is a better arrangement:

Keep the vector column. Drop the pgvector index.
A vector column with no index on it costs disk, not RAM — 24.7 GB of heap at 4M×1536, and heap pages are only read when you actually fetch a row. Postgres then gives you, for free:
  • The durable source of truth for rebuilding the external index — no separate vector store to own and back up.
  • Transactional writes, so the vector and its row still commit together (Day 2's argument survives on the write path).
  • The rerank corpus — fetch 200 full-precision vectors by ID, which is a b-tree point lookup.

"Metadata only" throws all three away and forces you to store vectors somewhere else durably anyway. Keeping the column and dropping only the index is strictly better, and it is the version to propose.

The crossover, and why leading with it is the strong move
The break-even sits between 10M and 100M vectors. Below it, external quantized ANN is more expensive — the operational load (~0.2 FTE ≈ $3,000/mo) swamps any infrastructure saving.

In a cost-focused interview, say the unflattering half first: "at our scale this would cost more, so I wouldn't do it." Then show you know exactly where it inverts and by how much. An engineer who proposes the clever architecture everywhere is a budget risk; one who can name the crossover is the person you hand the budget to.

Roll your own with mmap — when it is justified, and when it is ego

The minimal design is three files — vectors.bin, graph.bin, id_map.bin — mmap()'d at startup. You get near-zero load time, OS page cache handling residency, and multiple processes sharing one physical copy.

Justified when: you need an access pattern or a quantization scheme no library implements, or you are embedding into an existing C++ service where a dependency is unacceptable.

Not justified because: it looks impressive. FAISS and usearch already do this, with years of SIMD tuning and correctness fixes you would be re-deriving. In an interview, "I'd use usearch because it already mmaps and I'd rather spend the time on the rebuild pipeline" is a better answer than describing a custom index — it shows you know where the hard part actually is.

On agent-assisted delivery — the credible version of the claim
Coding agents genuinely compress the build: a FAISS service, a rebuild pipeline and a sync job that might be a four-week project can plausibly be a one-week one. Run quantization_cost_calc.py --build-weeks 1 and you will see what that is worth: at 100M vectors, $3,577/mo → $3,144/mo. A 12% improvement, not a transformation.

The reason is worth stating plainly, because it is the sophisticated point: agents compress build time, not operational load. The ongoing 0.2 FTE — on-call, incidents, rebuild babysitting, drift investigations — is most of the cost and does not shrink. Claiming an agent makes a service cheap to own will not survive contact with an experienced interviewer. Claiming it lets a small team reach an architecture that used to need a bigger one is true, defensible, and still impressive.

10. The Sizing Ladder — Ask These In Order

Everything above is a model. This is the interrogation order that feeds it. When someone hands you a RAG system to design, these are the questions, in sequence — and the point of the sequence is that each answer constrains the next, so by the time you reach the bottom the architecture is already determined.

The signal this sends
Notice that "which vector database should I use?" never appears on the ladder — it falls out of the bottom. That ordering is the whole tell. An engineer who opens with "we should use Pinecone" has picked a technology and will now reverse-engineer requirements to justify it. An engineer who opens with "how many chunks, and what does a miss cost?" is going to arrive somewhere defensible even if they have never used the tool they end up choosing.

Two of these are decisions you control, not facts you are handed

The version of this list that circulates treats every input as a given. Two of them are not, and they happen to be the two with the largest cost multiplier:

QuestionUsually treated asActuallyLeverage
Q2 — chunks per document "The ingestion pipeline emits what it emits." A retrieval-quality decision with a linear infrastructure cost. Halving chunk size doubles N, doubles index RAM, doubles the bill. 2–4×
Q3 — embedding dimension "The model outputs 1536, so we store 1536." MRL-trained models (text-embedding-3-*) let you truncate. 1536 → 768 is a config change, and §7 measured the recall cost as small. 2×

Combined, that is a 4–8× swing in infrastructure cost decided before a single row is indexed — larger than anything you can recover later by tuning ef_search. If you only get to influence two things on this list, these are the two.

The question everyone skips — Q5, filter selectivity

This one deserves its own paragraph because it can delete the problem. ANN indexes exist because scanning millions of vectors is too slow. But if every query is already scoped — this customer's transactions, this policy form in this state, this category and brand — then the candidate set after filtering may be small enough that exact search is not just viable, it is better: no recall loss, no index to rebuild, no graph decay, perfect reproducibility for audit.

effective corpus = N × filter selectivity
if that fits your latency budget, you do not need an ANN index

The trap is that latency and throughput fail separately. A filtered exact scan can comfortably meet a P99 SLA and still be unaffordable, because each query burns whole core-seconds and you are serving hundreds per second. Check both — the companion script does.

Read the insurance and fintech columns again
Two of the three domains end with "no ANN index" — and one of them is the 2-billion-vector case that looked like the hardest problem on the page. That is not a trick; it is what Q5 is for. The whole of §1–§9 exists to handle the retail column, where the filter genuinely does not save you.

This is also the answer to give when an interviewer describes a huge corpus and waits to see if you reach for a distributed vector database. "Before I size an index — what does a single query actually have to search? If every query is scoped to one card or one policy form, the corpus size is not the working set, and I'd want to rule out partition-plus-exact before building anything."

The interview answer

Good — demonstrates workload-driven reasoning
"I wouldn't choose pgvector or a dedicated vector database upfront. I'd estimate the expected number of chunks, embedding size, query volume, and growth rate. For up to a few million chunks that comfortably fit in memory, pgvector is attractive because it keeps metadata and vectors together and simplifies operations. As the dataset grows into tens or hundreds of millions of chunks, I'd separate metadata from vector search, introduce a dedicated ANN engine, and eventually shard and compress the vector indexes."

That is a solid answer and it will pass. The version below adds the two things a senior interviewer probes for next: a number attached to every claim, and the case where the answer is "no index."

Stronger — same reasoning, with the numbers and the escape hatch
"I'd size it before naming a product. Documents times chunks-per-document gives me N; N times dimension times 4 bytes gives me the heap; and pgvector's HNSW stores a full copy of each vector, so index RAM is roughly heap again — about 7 GB per million vectors at 1536 dims.

Before any of that I'd ask what one query actually has to search. If queries are scoped by customer, policy, or category, the filtered set may be small enough for exact search — and then there is no index to build, no recall to lose, and nothing to rebuild. I'd rule that out first because it is strictly the cheapest thing that works.

If it genuinely needs ANN: under about 10M chunks pgvector is the right call — one system, transactional writes, metadata and vectors together. From 25 to 50M it still holds once I apply fp16 and MRL truncation, which buys about 5×. Past roughly 100M the in-Postgres ladder is exhausted and I'd move the index to a dedicated engine with product quantization; our own numbers put that crossover between 10M and 100M, and below it the external option is more expensive once you price the operational load.

One caveat: with search on the OLTP instance I'd expect the CPU wall before the RAM wall, so the first move is usually a dedicated read replica, not a new database."

The same model, three domains, three different walls

This is the payoff of building a model instead of memorising a threshold — run it for each domain and you get genuinely different architectures.

Retail — 4M × 1536

index 28.6 GB · needs ~51 GB

Fits a 64 GB instance with ~20% headroom.

First wall: CPU, not RAM — at 500 QPS, search takes 1.5–2.5 cores from the same pool as checkout.

Move: dedicated read replica.

Insurance — 200k × 1536

index 1.4 GB · needs ~2.6 GB

Fits in shared_buffers on a laptop. At 20 QPS you use ~0.07 of one core.

No wall is reachable. You would need 35× the corpus and 100× the traffic to make any of this matter.

Move: stop optimising. Spend the effort on chunking, filter correctness, and audit.

Fintech txns — 2B × 768

index 7.4 TB · needs ~13.4 TB

Off the chart — 26× a 512 GB instance. Even binary quantization + exact rerank, the best rung on the ladder, still needs ~1.5 TB.

RAM wall by 26×, plus connection exhaustion. Replication cannot help — each replica needs the whole index.

Move: sharded store. This is Milvus's actual use case.

The trap in the insurance column
"No wall is reachable" is the right engineering conclusion and the wrong thing to say on its own in an interview — it sounds like you didn't think about scale. Say it as a bound: "at 200k chunks the index is 1.4 GB, so I'd have to grow 35× before RAM is even a conversation. That tells me the engineering belongs on retrieval correctness and auditability, not on the index." Knowing where the constraint isn't is as much a part of the model as knowing where it is — and it is what stops a team gold-plating infrastructure that will never be stressed.
The interview answer, in full
"pgvector's volume limit isn't a fixed row count — it's whether the HNSW index fits one machine's RAM, because traversal is serially-dependent pointer chasing and falling out of cache costs 25–100× on P99. At 1536 dims that's about 7 GB per million vectors. So: under 10M is trivial, 25–50M is viable once you apply fp16 and MRL truncation for a ~5× reduction, and past ~100M you've exhausted the in-Postgres ladder and sharding is the only structural answer. In practice I'd expect to hit the CPU wall before the RAM wall if search shares the OLTP instance — so the first move is almost always a dedicated read replica, not a new database."
