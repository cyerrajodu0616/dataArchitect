pgvector Fundamentals — IVFFlat vs HNSW

Week 2, Day 1 — how Postgres stores vectors, index anatomy, and the ANN tradeoff

Week 1 was about what vectors are and how to produce them. Week 2 is about where to put them and how to query them at scale. We start with pgvector — the choice your personal agent already uses — and go deep on how the two indexes (IVFFlat and HNSW) work so you can defend that choice in an interview.

Retail framing
Scenario
Your retailer's product catalog: 4 million SKU embeddings (1536-dim float32 vectors). Customers run ~500 concurrent search queries per second at peak (Black Friday). You need sub-100ms P99 latency. The question: can pgvector handle this, and which index type do you use?

1. How pgvector Physically Stores Vectors in Postgres

pgvector adds a native vector(n) column type to Postgres. Under the hood each vector is stored as a raw float4[] (array of 32-bit floats) in the table's heap pages — exactly like a regular array column. No separate storage engine.

-- Enable extension and create a table CREATE EXTENSION IF NOT EXISTS vector; CREATE TABLE products ( id BIGSERIAL PRIMARY KEY, sku TEXT NOT NULL, description TEXT, embedding vector(1536) -- 1536 float32 values per row ); -- Size on disk per row: 1536 × 4 bytes = 6,144 bytes ≈ 6 KB per embedding -- 4M SKUs × 6 KB = ~24 GB of embedding data (heap only, index is additional)

Before you slide to 3072: pgvector's index dimension limit
The explorer will happily size a 3,072-dim index for you, but pgvector will not build one on a vector column. An index entry must fit in a single 8 kB page, which caps indexes far below the column limits:

vector (float32)16,0002,000  (2,000 × 4 B = 8,000 B)

So text-embedding-3-large at 3,072 dims needs halfvec(3072) or MRL truncation to ≤2,000 — the column and the inserts work fine, and only CREATE INDEX fails, which is why teams hit this after embedding a whole corpus. Week 2 Day 2 §12 covers this alongside Postgres's other memory ceilings.
The nuance almost everyone gets wrong
"IVFFlat uses much less memory than HNSW" is the standard advice, and at 1536 dimensions it is barely true — try it on the slider above. Both indexes store a full copy of every vector (that is what "Flat" means in IVFFlat, and HNSW needs the vector at each node to compute distance during traversal). The only extra HNSW pays is the neighbour list, 2m × 8 bytes — about 4% of the index at 1536 dims.

Set dimensions to 128 and watch the gap widen: the neighbour list is a fixed cost, so it dominates when vectors are small. The real HNSW memory cost is at build time, not steady state — the graph must be constructed in memory, roughly 2× the final index size. That is the bar that turns red first.

Why does dimension matter so much for storage?

Each float32 value is 4 bytes. The math is straightforward:

  • 1536-dim (OpenAI text-embedding-3-small): 6 KB per vector
  • 768-dim (BGE-small): 3 KB per vector
  • 256-dim (MRL-truncated): 1 KB per vector

For 4M SKUs: 1536-dim = 24 GB heap. 256-dim MRL = 4 GB heap — a 6× RAM reduction for the Postgres shared_buffers hot cache. This is exactly why MRL truncation (Day 3, Week 1) matters operationally.

Plus index overhead: the HNSW index is roughly the same size again as the heap, because of the duplicated vector. Budget ~53 GB total for 4M × 1536-dim with HNSW. Week 2 Day 3 derives this precisely and shows why the common "30–60% overhead" rule of thumb understates it.

2. Exact Nearest Neighbor vs Approximate Nearest Neighbor (ANN)

A brute-force exact search computes the cosine similarity between the query vector and every single document vector, then returns the true k-nearest neighbors. This is called kNN (exact).

-- Exact search: no index, compares against EVERY row. -- Always correct. Always O(N). This is your ground truth. SELECT * FROM items ORDER BY embedding <=> '[0.1, 0.2, 0.3]' LIMIT 10;
Brute-force cost: O(N × d)    where N = corpus size, d = dimensions
4M SKUs × 1536 dims = 6.14 billion float multiplications per query

At 500 QPS: 6.14B × 500 = 3.07 trillion float operations per second. Even on a 96-core server this is ~32ms per query — borderline acceptable, but with zero headroom for concurrent queries, index misses, or Black Friday spikes.

ANN indexes trade a small amount of recall accuracy (returning 99% of the true k-nearest instead of 100%) for a 10–1000× speedup by avoiding exhaustive comparison. IVFFlat and HNSW both reduce the number of vectors examined; the amount they skip is controlled by probes and ef_search respectively.

Keep this in your pocket
Exact search is not just the slow fallback — it is the ground truth you measure recall against. Because you can force it in Postgres with SET LOCAL enable_indexscan = off, measuring your index's real recall is a scheduled job rather than a research project. Week 2 Day 5 builds exactly that job.

3. IVFFlat — Inverted File Index with Flat Quantization

IVF stands for Inverted File. IVFFlat organises vectors into clusters and searches only the clusters nearest your query — like a postal-code system for vector space. The "Flat" means vectors inside the selected clusters are compared directly, with no additional compression.

How it works

  1. During index creation, vectors are grouped into a fixed number of clusters (k-means).
  2. Each cluster has a centroid.
  3. For a query, the index finds the closest cluster centroids.
  4. It searches only the vectors inside those clusters, and returns the best candidates.

Animated: an IVFFlat query

IVFFlat Build Phase (Training)

  1. k-means clustering: Run k-means on all vectors to find lists centroids. Each vector is assigned to its nearest centroid and stored in that "list" (bucket).
  2. Index structure: A flat file of (centroid_id → list of vector_ids + raw vectors). No hierarchical tree.

IVFFlat Query Phase

  1. Find the probes nearest centroids to the query vector.
  2. Linear scan only those lists (skipping the rest of the corpus).
  3. Return top-k from scanned candidates.

Important parameters

ParameterWhen it appliesWhat it controlsRaising it…
listsBuild Number of clusters the corpus is partitioned into Makes each cell smaller, so a probe scans less — but with too many lists and too few probes, the true neighbours fall outside the probed cells and recall drops
probesQuery How many cells are searched per query Improves recall, increases latency roughly linearly. probes = lists is exact search
-- IVFFlat index creation -- lists: number of clusters (rule of thumb: sqrt(N) for N rows, max 1000-4000) -- For 4M rows: lists ≈ sqrt(4,000,000) ≈ 2,000 CREATE INDEX ON products USING ivfflat (embedding vector_cosine_ops) WITH (lists = 2000); -- Set probes at query time (session-level) SET ivfflat.probes = 20; -- search 20/2000 lists = 1% of corpus -- Higher probes = better recall, slower query -- probes=1: ~85% recall, fastest -- probes=20: ~95% recall, ~20x slower than probes=1 -- probes=2000: 100% recall = exact search (defeats the purpose)

Advantages

  • Conceptually simple — clusters and a linear scan
  • Leaner index than HNSW, and dramatically lower build memory
  • Much faster to build; realistic to rebuild nightly
  • Fast searches on large datasets
  • Search speed tunable at query time with probes
  • Cheap inserts — assign to the nearest centroid, no graph to mutate

Disadvantages

  • Requires training from existing data at build time
  • Cannot be built on an empty table
  • Poorly chosen lists/probes quietly reduces recall
  • Needs more tuning, and the right values depend on your data distribution
  • Centroids go stale as the catalog drifts — needs periodic rebuilds
  • Usually less accurate than HNSW at comparable latency
The IVFFlat cold-start problem: why you can't build it on an empty table

IVFFlat requires the k-means training phase to happen during CREATE INDEX. This means:

  • The table must contain at least lists × 1 rows before indexing (preferably lists × 10+ for good centroids).
  • For 4M rows with lists=2000: you need to load the full dataset before creating the index.
  • New rows inserted after index creation are still searchable but they don't update the centroids — they get assigned to the nearest centroid but aren't factored into cluster optimization.
  • Production implication: Rebuild the index periodically (weekly/monthly) as the catalog changes significantly. This is an operational cost pgvector imposes that managed vector DBs often handle automatically.

Week 2 Day 5's recall_monitor.py demonstrates this decay empirically — recall falls from 0.99 to 0.87 over six months of churn while every latency dashboard stays green.

4. HNSW — Hierarchical Navigable Small World

HNSW is inspired by the "six degrees of separation" principle in social networks. It builds a multi-layer graph where each vector is a node connected to nearby vectors. Higher layers hold fewer nodes and allow long-distance navigation; lower layers hold more nodes and provide detailed local search.

How it works

  1. Start at a node in a high-level graph layer.
  2. Move greedily toward nodes increasingly similar to the query.
  3. Descend through the layers when no closer neighbour exists at the current level.
  4. Search a neighbourhood in the lowest (densest) layer.
  5. Return the best candidates found.

It is like navigating a map by zooming in: country → city → street.

Animated: an HNSW traversal

Important parameters

ParameterWhen it appliesWhat it controlsRaising it…
mBuild Max graph connections per node per layer (default 16, range 4–64) Improves recall; increases memory and build time. At 1536 dims the memory cost is small (~4% of index); at low dims it is substantial
ef_constructionBuild Beam width while building the graph (default 64, range 4–400) Produces a better-connected graph and better recall at the same m; increases build time
ef_searchQuery Beam width during search (default 40) Improves recall, increases latency. Must be ≥ k
-- HNSW index creation -- Higher m → better recall + larger index + slower insert -- Higher ef_construction → better recall at same m + slower build CREATE INDEX ON products USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- At query time: control beam width during search SET hnsw.ef_search = 100; -- wider beam = better recall, slower query -- ef_search must be >= k (number of results requested) -- Default ef_search = 40

Advantages

  • Usually better recall than IVFFlat at the same latency
  • No separate clustering or training step
  • Can be built on an empty table
  • Handles incremental inserts well — no centroids to go stale
  • Strong low-latency performance and concurrent-query scaling
  • Fewer data-distribution assumptions to get wrong

Disadvantages

  • Higher memory use — and much higher peak memory during build (~2× the final index)
  • Slower to build; expensive on large datasets
  • Inserts and updates cost more — each one mutates graph links on neighbouring nodes
  • Deletes leave tombstones the graph keeps traversing until a REINDEX
  • Query performance is sensitive to m / ef_search

6. Which Should You Choose?

Choose HNSW when

  • Search quality and recall matter
  • You need low query latency
  • The dataset changes frequently
  • You have enough memory — including for the build
  • You want a good default with less cluster tuning

Choose IVFFlat when

  • Memory — especially build memory — is constrained
  • The dataset is large and relatively stable
  • You can invest in tuning lists and probes
  • Fast index creation matters (e.g. nightly full rebuild)
  • Slightly lower recall is acceptable
Practical rule of thumb
Start with HNSW if you want the best general-purpose performance and can afford its memory. Start with IVFFlat if memory efficiency and fast index creation matter more.

For most production retail deployments — a catalog that changes daily, latency-sensitive search, adequate RAM — HNSW is the default. Reach for IVFFlat when the build itself is the binding constraint.

7. Practical pgvector Queries for a Retail Catalog

-- Basic k-NN search (top 10 most similar products) SELECT id, sku, description, 1 - (embedding <=> '[...]'::vector) AS cosine_similarity FROM products ORDER BY embedding <=> '[...]'::vector -- <=> is cosine distance operator LIMIT 10; -- Operators: -- <=> cosine distance (1 - similarity; lower = more similar) -- <#> negative dot product -- <-> Euclidean distance (L2) -- Filter + vector search (e.g., only boots category) SELECT id, sku, description, 1 - (embedding <=> query_vec) AS score FROM products WHERE category = 'boots' -- pre-filter reduces scan size ORDER BY embedding <=> query_vec LIMIT 10; -- Monitor index usage EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM products ORDER BY embedding <=> '[...]'::vector LIMIT 10; -- Look for: "Index Scan using products_embedding_hnsw" in the plan
The pre-filtering problem — why WHERE + vector search is tricky

When you add a WHERE category = 'boots' filter, Postgres faces a choice:

  1. Post-filter (ANN then filter): Run ANN on all vectors, then apply WHERE. Fast ANN, but may return fewer than k results if many top ANN hits don't satisfy the filter.
  2. Pre-filter (filter then exact scan): Apply WHERE first to get candidate set, then do exact kNN within that set. Accurate but defeats ANN speed if the filter matches a large fraction.

pgvector uses a heuristic: if the filter is selective enough, it does exact search on the filtered subset; otherwise it falls back to ANN + post-filter.

Update: pgvector 0.8 added iterative index scans, which re-probe the index when a filter eliminates too many candidates instead of returning a short result set. This closes most of this gap. Turn it on with SET hnsw.iterative_scan = relaxed_order; (or ivfflat.iterative_scan).

Production workaround for extreme cases: Create separate pgvector tables per major category — each with its own HNSW index. Queries hit only the relevant table, eliminating the pre/post-filter dilemma entirely. Week 2 Day 2 compares this against Weaviate and Qdrant's native filtered-HNSW implementations.

8. Applied: A Product-Specific RAG on pgvector

The most common real use of everything above: answering questions about your products from your documentation. Manuals, FAQs, troubleshooting guides, policies, specifications.

Index choice for this workload
HNSW. A product knowledge base is thousands to hundreds of thousands of chunks — the index is small enough that HNSW's memory premium is irrelevant, while its advantages all apply: better recall, no cluster tuning, and clean handling of documents being added and updated over time. Note the correction to common intuition: HNSW uses more memory than IVFFlat, not less — it is simply that at this size the difference doesn't matter.

The pipeline

Schema and index

CREATE TABLE product_documents ( id BIGSERIAL PRIMARY KEY, product_id TEXT NOT NULL, content TEXT NOT NULL, metadata JSONB, embedding vector(1536) ); CREATE INDEX product_documents_embedding_hnsw ON product_documents USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- Index the filter column too — the planner needs it to filter cheaply. CREATE INDEX product_documents_product_id ON product_documents (product_id);

Retrieval query

SELECT id, content, metadata, 1 - (embedding <=> $1::vector) AS similarity FROM product_documents WHERE product_id = $2 -- never skip this ORDER BY embedding <=> $1::vector LIMIT 5; -- $1 = embedding of the user's question -- $2 = the product being asked about -- <=> is cosine distance under vector_cosine_ops; smaller = more similar
Design requirement: always filter by product
If your database holds documentation for more than one product, an unfiltered search will confidently return the descaling procedure for a different coffee machine. Store metadata with every chunk and filter on it:
{ "product_id": "coffee_machine_123", "document_type": "manual", "version": "2026-01", "section": "descaling", "language": "en" }
Depending on your data you may also need filters for model, region, language, documentation version, customer plan, user permissions, or document type. Note this interacts directly with §7's pre-filtering problem — with a highly selective product_id, enable pgvector 0.8's iterative scans.

The same pattern in insurance and fintech — and why the stakes differ

The mechanics are identical. What changes is the consequence of getting the filter wrong, and that changes how much engineering the filter deserves.

Retail — wrong product

product_id

Returns the descaling steps for a different coffee machine.

Consequence: a bad answer and a support ticket. Annoying, recoverable.

Insurance — wrong state or form version

carrier_id · state · form_version · effective_date

Returns the Texas version of a rider to an underwriter working a New York application, or a superseded form.

Consequence: a compliance incident. Life insurance forms are filed state by state; quoting the wrong one is a regulatory finding, potentially a rescission.

Fintech — wrong entity or jurisdiction

tenant_id · jurisdiction · product · as_of_date

Returns a disclosure that doesn't apply to this customer's account type or region.

Consequence: a mis-disclosure — a UDAAP/consumer-protection exposure, not a UX problem.

The insurance-specific requirement: temporal correctness
Retail documentation has one current version. Insurance does not — a claim filed today may need to be adjudicated against the form version that was in force when the policy was issued, which could be a decade old. Your retrieval must be able to answer "what did the contract say as of this date," not "what does it say now."

That makes the filter bitemporal, and it makes deletion nearly impossible — superseded forms must remain retrievable but must never surface for a new application. In practice: keep every version, filter on an effective-date range, and never delete. Note the pleasant side effect — a corpus you only ever append to has no graph decay from deletions, which is the Day 5 problem largely solved by the data model.

-- Insurance variant: bitemporal filter on top of vector search. CREATE TABLE policy_documents ( id BIGSERIAL PRIMARY KEY, carrier_id TEXT NOT NULL, product_code TEXT NOT NULL, -- e.g. 'TERM-20' form_number TEXT NOT NULL, -- e.g. 'ICC21-TL-NY' state CHAR(2) NOT NULL, effective_from DATE NOT NULL, effective_to DATE, -- NULL = currently in force content TEXT NOT NULL, metadata JSONB, embedding vector(1536) ); CREATE INDEX policy_documents_embedding_hnsw ON policy_documents USING hnsw (embedding vector_cosine_ops); -- Composite index supporting the filter, so the planner can be selective cheaply. CREATE INDEX policy_documents_scope ON policy_documents (carrier_id, state, product_code, effective_from, effective_to); -- "What did this contract say on the date the policy was issued?" SELECT form_number, content, 1 - (embedding <=> $1::vector) AS similarity FROM policy_documents WHERE carrier_id = $2 AND state = $3 AND product_code = $4 AND effective_from <= $5 -- $5 = policy issue date AND (effective_to IS NULL OR effective_to > $5) ORDER BY embedding <=> $1::vector LIMIT 5;
This is your data-engineering wedge, stated plainly
Slowly-changing dimensions, effective dating, bitemporal history, append-only audit tables — you have been building these for 14 years. Most GenAI engineers approach a RAG corpus as a folder of documents to embed. In a regulated domain it is a versioned dimension with a validity window, and treating it that way is the difference between a demo and a system that survives an audit. Say exactly this in an insurance or fintech interview.
Fintech: know which corpus you are talking about
"Fintech RAG" hides two completely different workloads, and conflating them is a common interview stumble:
  • Document retrieval — disclosures, policies, dispute procedures, KYC guidance. Tens of thousands of chunks. Identical to the insurance case; pgvector with HNSW defaults.
  • Transaction / merchant embeddings — hundreds of millions to billions of vectors for fraud similarity and merchant normalisation, at thousands of QPS with sub-second freshness. A different architecture entirely — Day 3 shows exactly where this crosses the line.

What matters more than the index choice

For a small RAG system, retrieval quality is affected far more by the following than by IVFFlat vs HNSW:

FactorGuidance
1. Chunking Split on semantic boundaries — section, heading, procedure, FAQ entry, troubleshooting issue. Each chunk should contain one coherent piece of information. This is Week 3 Day 1's whole topic.
2. Metadata Store product_id, title, section, version and language with every chunk. Metadata is what makes filtering — and later, debugging a bad answer — possible.
3. Retrieval count Start at 3–8 chunks. Too many adds irrelevant content and burns context window, which measurably degrades answer quality.
4. Reranking Retrieve 10–20 candidates with HNSW, rerank with a cross-encoder, pass the best 3–5 to the LLM. Week 1 Day 4's finding: "90% of retrieval failures are solved by reranking, not fine-tuning."
5. Prompt grounding Explicitly instruct the model to answer only from retrieved context and to say when it doesn't know.
-- Chunking: bad (one blob, several unrelated topics) "The product has several features, installation requirements, warnings, maintenance instructions, and warranty limitations..." -- Chunking: good (one coherent topic per chunk) "Descaling the machine Run the descaling cycle every three months..." "Power requirements The device requires a 220-240 V power supply..."
Answer the user's question using only the provided product documentation. If the answer is not present in the documentation, say that you do not have enough information. Do not invent specifications, procedures, or compatibility details. Retrieved documentation: {context} User question: {question}
Recommended starting architecture
Postgres + pgvector · HNSW index · cosine distance · product and document metadata in JSONB · metadata filtering on every query · retrieve 5–10 chunks · reranking added later if needed · a grounded-answer prompt · and an exact-search evaluation set so you can actually measure recall.

You almost certainly do not need IVFFlat here unless the corpus grows very large or build memory becomes a real constraint.
