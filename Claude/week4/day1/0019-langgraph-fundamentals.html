LangGraph Fundamentals — Why Agents Need Loops

Week 4, Day 1 — starting from zero: what a state machine is, and why a chain can't do the job

Before anything else — what are we even building?

An agent is a program that decides what to do next instead of being told. That's it. That's the whole definition.

A normal program: "read the file, transform it, write it out." You wrote the order. It never changes.

An agent: "here's a customer message and some tools. Figure out what they want and handle it." The order of operations depends on what it finds along the way — and that's the only real difference.

Agent orchestration is the plumbing that decides how it gets to choose. That's this whole week.

1. Two Shapes: A Line and a Board Game

There are two ways to organise the steps an agent takes, and almost everything this week comes back to the difference.

In plain words

A chain is a recipe. Step 1, step 2, step 3, done. You always go forward. You never go back to step 1.

A graph (state machine) is a board game. There are squares, and after each square you look at the board to decide where to go next. You're allowed to go back to a square you've already been on.

That one difference — being allowed to go backwards — is what today is about.

Anchoring this to what you already know

You've built plenty of pipelines. A chain is an Airflow DAG: tasks with dependencies, strictly one direction, no cycles allowed — the "A" in DAG literally means acyclic.

A state machine is the same picture with the acyclic rule removed, plus one shared object that every step reads and writes.

Where the analogy holds: nodes are tasks, edges are dependencies, and you can draw both on a whiteboard the same way.

Where it breaks — and this matters: in Airflow the graph is fixed before the run starts. In an agent, the path is decided during the run, by data that didn't exist when you deployed. That's why you can't just look at the diagram and know what happened; you have to look at the trace.

2. The Three Words You Need

The vocabulary is genuinely small. Three terms, and here's each one twice — once in plain words, once in something you already write every day.

state
Plain: a bag of everything known so far. Starts nearly empty, fills up as the agent works.
In your terms: one row in a table that you keep running UPDATE on. Columns get filled in as you go.
node
Plain: one step. It reads the bag, does something, and puts something back in the bag.
In your terms: an UPDATE statement. Takes the row, changes some columns.
edge
Plain: the arrow saying what happens next. A plain edge always goes to the same place. A conditional edge looks in the bag and picks.
In your terms: a CASE / WHERE that decides which statement runs next.
state = a row  ·  node = an UPDATE  ·  edge = a CASE deciding what runs next

If you hold onto that one line, the rest of the week is detail.

3. The Smallest Real Example

A customer messages a retailer. We want to handle it. Here are the steps:

NodeWhat it doesWhat it puts in the bag
classifyWork out what they wantintent, confident
lookup_orderFetch their orderorder
check_policyIs it inside the 30-day window?within_window
approve / escalateDecidedecision

Now the customer sends this:

"hi, this isn't what I expected"

Read it again. It never says what they want. Not a refund, not tracking, not a cancellation. This is completely normal — most real messages are like this — and it is exactly where the two shapes stop being equivalent.

What the chain does

python state_machine_trace.py step 1: classify intent = 'unknown' (new) confident = False (new) step 2: lookup_order order = {'item': 'laptop sleeve', 'days_since_delivery': 9, ...} step 3: check_policy within_window = True step 4: decide decision = 'APPROVED' RESULT: APPROVED WHY : GUESSED that an unclear request meant refund, because there was nowhere else to go
Look at step 1 and then step 4
The chain knew it was confused — confident = False is right there in the state. And it approved a refund anyway.

Not because the code is bad. Because a chain only has forward arrows. Once you're at classify and you're unsure, the only arrow available points at lookup_order. There is no arrow that means "hang on, let me ask." So it guesses, and it just gave money to someone who wanted a tracking number.

What the graph does

Two separate turns happen at step 2, and it matters that you can tell them apart — the bot has to actually send its question before it can possibly receive a reply to it. Here they are kept on separate lines instead of compressed into one arrow:

step 1: classify intent = 'unknown' confident = False branch chose: ask_clarify <-- a choice the chain couldn't make step 2: ask_clarify [turn 1 — the customer's original message, still sitting in the bag] request = "hi, this isn't what I expected" [turn 2 — the retail bot's OWN first request, sent back to the customer] question_asked = 'Sorry — did you want a refund, tracking, or a cancellation?' [turn 3 — the customer's follow-up reply, appended, not overwritten] request = "hi, this isn't what I expected | user said: no i just want to know where is my parcel" clarify_count = 1 step 3: classify <-- BACK to step 1, with more in the bag intent: 'unknown' -> 'track' confident: False -> True branch chose: handle_track step 4: handle_track decision = 'SENT_TRACKING' RESULT: SENT_TRACKING PATH : classify -> ask_clarify -> classify -> handle_track
In a real deployment, step 2 is actually two steps with days in between
The script answers its own clarifying question instantly so it can run end-to-end without a human sitting at a keyboard. A production agent does not get to do that: ask_clarify sends its question and then the run stops — there is no reply yet to put in the bag. Only once the customer actually answers does anything resume, and that resume has to find the run exactly where it left off. That pause-and-resume mechanic is its own topic (Day 3), and it only works at all because the state was saved somewhere durable (Day 5).
Read the PATH line — classify appears twice
That's the whole lesson. Same nodes, same logic inside each node, same model if there were one. The only difference is one arrow pointing backwards.

Chain: APPROVED — gave a refund to someone who wanted a tracking number.
Graph: SENT_TRACKING — sent its own question first, then asked one question and got it right.

Try this
Run python state_machine_trace.py and read the trace next to the source. The whole engine is about 40 lines at the top of the file — nodes, edges, branches, and a while loop. There is nothing else in it. That is genuinely what LangGraph is, before it adds checkpointing and a nicer API.

4. The Trap Everybody Hits First

Loops are the point. Loops are also how you burn $4,000 overnight.

python state_machine_trace.py --runaway step 3: classify branch chose: ask_clarify step 4: ask_clarify clarify_count: 1 -> 2 step 5: classify branch chose: ask_clarify step 6: ask_clarify clarify_count: 2 -> 3 !! HALTED: step limit 6 exceeded path was: classify -> ask_clarify -> classify -> ask_clarify -> ...
Every cycle needs an exit condition that is guaranteed to fire
In the working version the exit is: give up after 2 clarifying questions and hand to a human. Not "loop until the model is confident" — a model that is confused about a genuinely ambiguous message will stay confused forever, and every trip round the loop is another paid LLM call.

The step limit is a backstop, not the exit condition. If the step limit is what stopped your agent, you have a bug, not a design. This distinction is worth saying out loud in an interview, because "we set recursion_limit=25" is a very common answer and it is an answer about the seatbelt, not the brakes.

You already know this pattern
It's a retry loop with a max-attempt count, and you'd never ship one without the counter. The only new thing is that the "attempt" costs an LLM call rather than a database round-trip — so the runaway is expensive as well as slow.

5. When Do You Actually Need a Graph?

Not always. This matters, because reaching for a framework you don't need is its own failure.

If your workflow…UseWhy
Always runs the same steps in the same orderA chain, or plain functionsA graph adds concepts and gives you nothing back. Don't.
Needs to retry a step with different inputGraph"Retry" is a backward edge. You can fake it with a while loop, and past two of them you've written a worse graph engine.
Needs to ask a human and continue afterwardsGraphYou must pause, persist, and resume at the right node. Day 3 and Day 5.
Picks different tools depending on what it findsGraphThat's a conditional edge.
Might loop an unknown number of timesGraphAnd it needs an exit condition. §4.
Is one LLM call with a tool or twoJust call the APIDay 2 makes this case properly. It's more often right than the ecosystem suggests.
The honest test
Count the backward edges. Zero backward edges means you have a pipeline, and you should build a pipeline. One or more means you have a state machine, whether or not you use a framework — and at that point using one is bookkeeping you don't have to write yourself.

6. The Same Idea in Three Domains

Retail — support agent

classify → ask → classify
→ lookup → policy → decide

Loop: ask a clarifying question when intent is unclear.

Exit: hand to a human after 2 questions. Customers won't answer a third.

High volume, low value per interaction — the loop must be short because every extra turn multiplies across millions of conversations.

Insurance — underwriting assistant

gather → check_missing → gather
→ assess → human_review

Loop: keep requesting missing evidence — labs, APS, MVR — until the file is complete.

Exit: complete, or a deadline, or the applicant stops responding.

Loops can run for weeks. That makes state persistence (Day 5) load-bearing rather than a nicety — the process outlives any process.

Fintech — dispute handler

intake → classify_reason
→ gather_evidence → decide

Loop: pull more evidence when confidence is below threshold.

Exit: a hard regulatory clock — the network deadline doesn't care about your confidence.

The exit condition is set by law, which is the cleanest version of this: the deadline is a real thing, not a tuning parameter.

Notice what differs across the three
The shape is identical in all three — a gather/check loop feeding a decision. What differs is the exit condition, and in each case it comes from the business, not from engineering: customer patience, an underwriting deadline, a regulatory clock.

That's the thing to notice as an architect. The interesting design decisions in an agent are almost never "which framework" — they're "when does this stop, and who decided that."

7. What LangGraph Adds On Top

The 40-line engine in the companion script is a real state machine. LangGraph is that plus the things you'd otherwise write yourself:

FeatureIn plain wordsCovered
CheckpointingSaves the bag after every step, so you can crash and resume.Day 5
InterruptsStop before a node, wait for a human, carry on later — possibly days later.Day 3
State reducersRules for merging changes, e.g. append to a message list rather than overwrite it.below
StreamingEmit each step as it happens, so a UI can show progress.—
Parallel branchesRun independent nodes at once and merge the results.Day 4
State reducers — the one piece the toy engine gets wrong

Our engine does state.update(changes), which overwrites. That's fine for intent — the new value replaces the old. It is wrong for a conversation history: overwriting messages would throw away everything said before.

LangGraph lets you declare, per field, how updates merge. Overwrite for scalars; append for lists.

class State(TypedDict): intent: str # overwrite (default) messages: Annotated[list, operator.add] # append instead

Why it matters beyond convenience: once nodes can run in parallel, two of them may write the same field. Overwrite means last-writer-wins and the result depends on timing. A declared reducer makes the merge deterministic — which is the difference between a bug you can reproduce and one you can't.

If that sounds familiar, it should: it's the same problem as concurrent writes to a row, and a reducer is the same answer as an atomic UPDATE ... SET x = x + 1 instead of read-modify-write.
