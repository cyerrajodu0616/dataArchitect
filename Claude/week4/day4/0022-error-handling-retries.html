Error Handling — Why Reliable Steps Make an Unreliable Agent

Week 4, Day 4 — compounding failure, the three kinds of error, and the retry that costs you money

Start with the arithmetic that surprises people

A step that works 99% of the time is a good step.

If their failures are independent and every step is required, six in a row work 0.996 = 94.1% of the time.
Twelve work 88.6%. Twenty work 81.8%.

Under that model, reliability multiplies along a required path. Real failures may be correlated, optional branches are weighted by traffic, and retries change the effective step probabilities, so use the product as a baseline rather than an SLO forecast.

You've met this before
It's the same maths as a multi-stage ETL pipeline where each stage has a small failure rate, or a microservice call chain. The difference is that agent steps are LLM calls — so each retry costs money, takes seconds, and may produce a different answer than the attempt before it.

1. What Step Count Actually Costs

The design consequence, which runs against instinct
The cheapest reliability work is deleting a step. Every node you add is a multiplication, not an addition.

That runs directly against the instinct to decompose an agent into many small, clean, single-responsibility nodes. Decomposition is good for readability and bad for reliability, and the tradeoff is real. Prefer fewer, bigger nodes than you would in ordinary code — and when someone proposes splitting a node in a design review, the honest question is "what does that do to end-to-end success?"

2. Three Kinds of Failure — and Only One Is Easy

KindIn plain wordsWhat to do
Transient The network blipped. The API returned 503. You got rate limited. Retry. It'll probably work.
Permanent The input is invalid. The policy doesn't exist. You lack permission. Don't retry. It will fail identically every time and each attempt is billed.
Ambiguous You sent the request and never saw the response. Did the refund go out or not? This is the hard one. §4.
retries end-to-end failed/mo extra calls/mo extra $/mo ------------------------------------------------------------------ 0 94.1% 76,076 0 0 1 98.5% 19,812 78,000 312 2 98.5% 19,382 156,000 624 3 98.5% 19,379 234,000 936 CEILING: even with infinite retries you reach 98.5%, because 25% of failures are PERMANENT and retrying them buys the same error at full price.
Read the ceiling, and the flat column
The first retry buys a lot: 94.1% → 98.5%. The second and third buy essentially nothing and cost $312/month each. That's because everything retryable was already recovered on attempt two, and what's left is permanent.

So the first question is not "how many retries?" — it's "can I tell transient from permanent?" A policy that can't distinguish them spends 25% of its retry budget on requests that are guaranteed to fail, and no amount of tuning fixes that.

3. The Failure Mode Specific to Agents

Classical retries assume the operation is deterministic — retry it and you get the same thing, or you get a success. LLM steps break that assumption in two directions:

SituationWhy it's differentWhat to do
The model returned malformed output A plain retry re-rolls the dice and might work. But you learned nothing. Retry with the error in the prompt — "your last output failed validation because X". Far higher success than a blind retry.
The model called the wrong tool Not a failure at all from the runtime's point of view. It succeeded, at the wrong thing. A validation node after the tool call. This is a correctness check, and retry logic will never see it.
The model loops Day 1's runaway. Each turn "succeeds"; the run never ends. A step limit as backstop, and a real exit condition. Not a retry problem.
The retry that's actually worth building
Retry with the error fed back in. A blind retry of a malformed-output failure re-rolls the dice; a retry that says "that failed schema validation: days_since_delivery must be an integer" usually succeeds first time. It costs one extra sentence in the prompt and converts a coin flip into a fix.

Operationally, this is a new model attempt with validation feedback, not a transport retry of the same request. Track it separately: it consumes model budget, may change semantics, and still needs a hard attempt limit.

4. The Ambiguous Failure, and Why Retries Make Things Worse

The scenario, in plain words

Your agent calls the refund API. The connection drops before the response comes back.

Did the refund go out? You genuinely don't know.

Retry, and you might refund them twice. Don't retry, and you might have refunded nobody. Neither choice is safe without an idempotency key. With a receiver-enforced key, stable payload, atomic key/result storage, and a defined retention window, retry becomes safe against duplicate execution.

python reliability_math.py --domain insurance duplicate side effects $/month -------------------------------------------------------------------- without idempotency keys 4 67,392 with idempotency keys 0 0 0.156% of runs hit an ambiguous failure. That sounds small. At 2,400 runs a month and $18,000 per side effect it is $67,392 a month, and the fix is a UUID in a header.
Say this precisely — it's the distinction interviewers listen for
"Add retries" is not a complete answer to "how do you handle failures". The complete answer is "retries plus idempotency keys, and here's which operations need them" — because retries alone make availability better and correctness worse.

And note the order: idempotency keys go in before retries, not after. Shipping retries first means shipping the duplicate-side-effect bug and discovering it in production, on the operations that cost the most.

The idempotency key is just a primary key
Generate a UUID per logical operation, send it with the request, and have the receiver store it with a unique constraint. Second request with the same key returns the first result instead of doing the work again.

You've built this — it's an upsert with a natural key, or a dedup table on a stream. The only new thing is remembering that the key must be derived from the logical operation (this refund for this order), not generated fresh on each attempt. A key regenerated per attempt is no key at all, and it's the most common way this gets implemented wrong.

5. Retry Storms — Why Backoff Alone Isn't Enough

A dependency has a 5-second outage. Everything in flight fails at the same instant. Now they all retry.

StrategyWhat happens
Fixed 1s delayEvery client retries at the same moment. The recovering dependency is hit by the full load at once and falls over again.
Exponential backoff, no jitterBarely better. They all failed at the same instant, so they all wait 1s, then 2s, then 4s — in lockstep. They stay synchronised.
Exponential backoff + full jitterRetries spread across the window. Load arrives smoothly and the dependency recovers.
The one-line fix people leave out
sleep(random.uniform(0, backoff)) instead of sleep(backoff).

Exponential backoff on its own doesn't break the synchronisation that caused the storm — jitter is what does. It's the difference between a dependency that recovers in seconds and one that oscillates for an hour. If you name only one of these in an interview, name jitter, because it's the half that gets forgotten.

Above both sits the circuit breaker: after N consecutive failures, stop calling entirely for a cooling-off period. Retries assume the dependency is basically healthy. A breaker is what you have for when that assumption is false.

The breaker also closes Day 3's gap
Day 3's approval model priced errors one at a time and explicitly couldn't handle correlated failure — a bug that makes the agent wrong the same way 4,000 times isn't 4,000 independent small losses, it's one incident.

A circuit breaker on the error rate, not just on connection failures, is what stops that at 40 instead of 4,000. Trip it when the agent's own confidence or validation-failure rate spikes, and route to humans until someone looks. That's the control the threshold arithmetic couldn't provide.

6. Three Domains

Retail

6 steps · 99% · 94.1%
1.3M runs/mo

76,000 failed conversations a month before any retries. Short graphs, but volume turns a small per-step rate into a staffing problem.

Side effects are cheap ($42), so the priority is availability: retry aggressively, keep the dead-letter path automated.

Life insurance

14 steps · 98.5% · 81%
2,400 runs/mo

One run in five needs intervention. Long graphs are the problem here — this is where "delete a step" pays most.

And a duplicate side effect is a policy bound twice — a rescission and a regulatory conversation, not a refund. 4/month × $18k = $67,392.

Fintech

9 steps · 99.2% · 93%
45k runs/mo

Middle everything, but with a hard deadline. A run that fails and needs manual restart may miss the network window.

The cost of a failed run isn't the retry — it's the automatic loss when the clock runs out. Which makes the dead-letter path a compliance control.

7. What to Build, In Order

#Do thisWhy here
1Delete a step.Reliability multiplies, so this is the cheapest win available. Do it before tuning any policy.
2Classify the failure — transient / permanent / ambiguous.A policy that can't tell them apart wastes 25% of its budget and cannot be made safe.
3Idempotency keys on every side-effecting operation.Before retries, not after. Retries without keys actively make things worse.
4Exponential backoff with jitter.Backoff without jitter keeps clients synchronised and is barely better than a fixed delay.
5Circuit breaker, on error rate as well as connection failure.For when the dependency is genuinely down — and for the correlated-failure case Day 3 couldn't price.
6A dead-letter path with state attached.Some runs won't succeed. They need somewhere a human looks, and the state must be there so the run can be resumed rather than restarted from scratch.

What an idempotency key does not guarantee
It does not make an arbitrary client safe by itself. The receiver must enforce uniqueness and persist the key, request fingerprint, and result atomically with the side effect. Define key scope and retention, reject payload conflicts, and preserve the original key when replaying a dead letter.
