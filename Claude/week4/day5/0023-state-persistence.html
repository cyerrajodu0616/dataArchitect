State Persistence — Checkpoints, the Quadratic, and Why Postgres

Week 4, Day 5 — what "save the agent's progress" actually costs

What a checkpoint is

After every step, the agent writes down everything it knows so far. That saved copy is a checkpoint.

It's what makes two things possible, and Day 2 showed they're the same requirement: surviving a crash, and pausing for a human and coming back three days later.

Think of it as a save file in a game. Except it's saved on every single move, and there might be a million games running.

1. Resuming Is a SELECT

Before any sizing, it's worth seeing that there's no magic here:

CREATE TABLE agent_checkpoint ( thread_id uuid NOT NULL, -- the run. Day 3's resume key. step int NOT NULL, node text NOT NULL, -- where to resume state jsonb NOT NULL, -- full, or a delta is_full boolean NOT NULL, -- delta chains need an anchor created_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (thread_id, step) ); -- a useful mental model for locating the latest saved state: SELECT node, state FROM agent_checkpoint WHERE thread_id = :id ORDER BY step DESC LIMIT 1;
That's the minimum mental model, not the whole checkpointer
A durable implementation stores checkpoint identity, channel/version metadata, pending writes, parent relationships, configuration, and serialization data in addition to user state. thread_id selects a checkpoint history; it is not necessarily the table's sole primary key. The simplified query explains the persistence idea, while the framework also handles consistent snapshots and resumption protocol.

2. The Estimate Everyone Makes, and Why It's Wrong

The natural sizing is runs × steps × state_size. It's wrong, and the reason is worth internalising because it changes the answer by 3–9× depending on the domain and how many steps the agent takes — and the gap gets worse the more capable (and longer-running) the agent gets.

In plain words

The state grows as the run goes on. Step 1's state is a question. Step 12's state is a question plus eleven tool results plus the whole message history.

So if you save the entire ever-growing state at every step, you're not writing the same size N times. You're writing 1, then 2, then 3… and the total is 1+2+3+…+N. This is a sizing model, not a promise about every checkpointer's physical encoding or compression.

total bytes per run = N(N+1)/2 × growth  →  quadratic in step count

3. The Three Levers, In Order

#LeverRetail effectWhat it costs you
1 Trim the state — stop storing raw tool output nobody re-reads ~65% reduction Usually low cost, but retain the inputs needed for replay, audit, and debugging. It shrinks write rate, WAL, replication, backup, and the prompt if that state is passed to the model.
2 Delta checkpoints — write only what changed 113 GB → 29 GB You can't read one checkpoint standalone any more; you replay from the last full anchor. Slightly slower resume, more code.
3 Shorter retention Linear in days Usually not an engineering decision at all. See insurance below.
Why trimming comes first, and why it's usually skipped
Most agent state is raw tool responses — the full JSON from an order lookup when the agent needed three fields. Storing the whole payload is the default because it's easier, and it's the single biggest contributor to both the base size and the growth rate.

It usually compounds: the same trim reduces storage, write volume, WAL, replication lag, restore time, and — if that state is being serialised into prompts — token cost. The constraint is evidence: preserve normalized decision inputs, hashes or references required for audit, and enough context to replay safely.

4. Does It Belong in Postgres?

ADR-002 put vectors in Postgres. The same argument applies here and is stronger, for a reason that usually gets left out of the Redis-vs-Postgres discussion:

The transactional argument
Co-locating checkpoints and business records in Postgres makes a single-transaction design possible only when your integration deliberately writes both through the same database transaction. A framework checkpointer and a separate business call do not become atomic merely because both use Postgres.

If the side effect is external, use its idempotency protocol plus an outbox/inbox or reconciliation path. Splitting state across systems adds coordination work, but co-location alone does not remove the dual-write problem.

ConcernPostgresRedis (or a dedicated store)
Write rateRetail checkpoints are 12/sec peak against 2,400/sec of existing OLTP — 0.5%. Noise.Solves a problem you don't have at this rate.
TransactionalityCan share a transaction with local business writes if the application integrates them that way.Requires an explicit cross-system consistency protocol.
Backup / restoreOne restore. Business data and agent state come back consistent.A restore that recovers business data but not agent state leaves in-flight runs pointing at rows that moved.
AuditFor insurance the checkpoint history is the audit trail — same artifact, same lifecycle.Separate retention, separate compliance story.
LatencyA few ms per write.Faster — matters only if state is large, hot, and read every step.
When it stops being Postgres — say this before being asked
1. Checkpoint writes become a large share of a shared OLTP instance's write load. Measure it; retail's 0.5% is nothing, but a 30-step agent at the same volume is a different conversation.
2. State is large and hot and read every step — then Redis for hot, Postgres as the durable tier, and treat Redis as a cache you're allowed to lose.
3. Runs are so short nothing needs to survive. Then don't checkpoint at all — an in-memory saver is a legitimate choice and almost nobody suggests it.
One operational detail worth knowing
If retention is short, partition by created_at and drop partitions. A DELETE at 7.8M rows/month generates WAL, bloats the table, and hands autovacuum work nobody budgeted for. Dropping a partition is instant and generates almost nothing. You've made this call before on event tables — it's the same call.

5. Three Domains, Three Different Problems

Retail

6 steps · 1.3M runs/mo
3-day retention

A write-rate question, not a storage one. 7.8M writes/month = 12/sec peak, which is 0.5% of existing OLTP load. Free.

Retention can be brutal — a finished conversation is worth nothing once the customer leaves. Partition and drop daily.

Life insurance

14 steps · 2,400 runs/mo
2,555-day retention

The opposite shape. Tiny volume, long runs, big state — and seven years of retention because the checkpoint history is the audit trail of how the decision was reached.

You cannot delete your way out, so the quadratic matters most here: 458 GB full vs 57 GB delta. Delta checkpointing isn't an optimisation, it's the design.

Fintech

9 steps · 45k runs/mo
180-day retention

Middle everything, but note the OLTP baseline: 4,000 writes/sec of transaction traffic on the same instance.

Retention is set by dispute-window rules, not by engineering. Measure the checkpoint share before assuming it's free.

6. Lab: Treat a Checkpoint as a Lifecycle

checkpoint_lifecycle_lab.py uses a real LangGraph InMemorySaver to inspect checkpoint history, then models the production controls a storage backend must enforce. InMemorySaver is intentionally for tests and local exploration; a production deployment needs a durable saver such as Postgres.

Lifecycle concernInvariant
Identity and isolationEvery invocation uses configurable.thread_id; histories for different threads never merge.
Lease ownershipOnly one worker may resume a checkpoint version while its lease is live.
Optimistic versionA stale worker cannot overwrite state produced by a newer resume.
Lease expiryA crashed worker does not lock the run forever; another worker may take over after TTL.
Terminal protectionCompleted or rejected runs cannot be resumed into a second side effect.
Schema migrationOld state is upgraded explicitly before new node code reads it.
State minimizationKeep decision inputs and references; remove raw payloads and direct PII only when replay/audit obligations remain satisfied.

From test saver to production saver

# InMemorySaver is for deterministic tests only. # Production requires the separate Postgres checkpoint package. from langgraph.checkpoint.postgres import PostgresSaver with PostgresSaver.from_conn_string(DB_URI) as saver: saver.setup() # one-time schema setup; run as a controlled migration app = graph.compile(checkpointer=saver) config = {"configurable": {"thread_id": case_id}} app.invoke(input_state, config=config) latest = app.get_state(config) history = list(app.get_state_history(config))

Two workers resume one approval

checkpoint version 7 is READY worker A: compare version=7, acquire lease ---- wins; status RUNNING worker B: compare version=7, acquire lease ---- rejected; lease is live worker A: execute, save version 8, release ---- status TERMINAL worker B: retry after refresh ---- rejected; terminal state The compare-and-set, lease, business idempotency record, and terminal write must be enforced atomically by the durable store—not by an in-process dict.
Production operationRequired decision or signal
Serializer safetyUse an allow-listed format; do not deserialize attacker-controlled executable objects.
PII and encryptionMinimize direct identifiers, encrypt in transit and at rest, control key access, and preserve audit references.
RetentionPartition by creation time where appropriate; expire only after legal, replay, and incident needs are met.
Restore drillRestore checkpoint and business timelines together, then resume test threads without repeating side effects.
ObservabilityMeasure save/load latency, checkpoint bytes, pending age, lease conflicts, stale resumes, migration failures, and restore success.

Deploys change stored data contracts
A multi-day run may resume under code that did not create its checkpoint. Version state schemas, make migrations deterministic and backward-compatible, and test at least the oldest still-retained version. A deploy without a checkpoint migration plan is a data migration without a plan.
